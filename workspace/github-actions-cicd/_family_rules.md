# Family rules — github-actions-cicd (as of 2026-10-30)

Policy decisions applied identically in every skill of the family. Numbered, short, testable.

1. Evidence rule: a claim in Always Do / Never Do needs a versioned official source read in full.
2. Tags are plain parentheses: `(medium confidence)`, `(unverified)`; never bold or brackets.
3. One claim per Always Do bullet; Never Do alternatives are High confidence too.
4. Every third-party action in an example is pinned by full commit SHA with the tag as a trailing comment; SHAs come only from `_family_facts.md` (F2-F10). Do not restate github-core's SHA-pinning and injection guidance — link to `automating-github-repos-with-actions`.
5. Building-block naming (reason: F16, workflows cannot sit in subfolders): callers `ci-<app>.yml` (pull_request), `cd-<app>.yml` (merge/release), `ops-<task>.yml` (schedule/dispatch); reusable workflows `_<domain>-<name>.yml`; composite actions in `.github/actions/<domain>/<name>/action.yml`.
6. Every reusable workflow declares typed `inputs`, explicit `outputs`, each secret by name (no `secrets: inherit` in examples, F19), and its own minimal `permissions`.
7. Pull-request workflows never write to cloud, never apply, never deploy to a shared environment; `id-token: write` only on the job that logs in.
8. Build once, promote the same artifact (image digest or zip hash) across environments; never rebuild for prod.
9. Cloud login is keyless where the cloud officially supports it (AWS OIDC, F3); OCI uses API key in environment secrets by default and token exchange (F20/F21) only as a medium-confidence option (DEC-002).
10. Environment-scoped secrets, never repository-scoped, for anything that can deploy.
11. Version pins in examples follow `_family_facts.md`; a skill never states a newer or different version than the facts file.
12. Cross-package references are by skill name only (e.g. `deploying-aws-lambda`, `provisioning-aws-iam-v6`, `vercel-cli-with-tokens`); never copy their content and never make them a hard dependency except github-core.
13. Pull-request (preview) jobs log in with a dedicated PR-only read role/environment (e.g. `<env>-pr`), never with the credentials of a deployable environment, because branch code runs during plan/build — decided in pilot (finding M2, DEC-008).
14. Every skill ends its SKILL.md navigation with a Verification Loop (offline commands + expected output) — decided in pilot (finding M1).
15. Examples use the real paths `./.github/workflows/_<name>.yml` and `./.github/actions/<domain>/<name>` (verifier exception for this package, G2 DEC-010); never the `<repo-workflows-dir>` placeholder.
16. Plan variants (G2 DEC-011, user decision DEC-012): DEFAULT = GitHub Pro/Team private repos: environments with secrets/variables and deployment branch policy `main` (F25), protected `main` with required PR reviewers (F39) so the human approval is the PR review of the rendered plan/diff before merge; cloud roles trust `environment:<env>`. FREE private variant (documented as weaker, never silently): no environments, no protected branches; only OIDC with roles trusting `ref:refs/heads/main` (no static deploy secrets where the cloud allows it), dev/prod separated by account/role or repo, accepted risk stated; where a static secret is unavoidable (OCIR, Vercel) it is a repository secret with least privilege and an explicit warning. Required reviewers / wait timers / artifact attestations = upgrade path for public repos or Enterprise. The executor asks the plan before generating CD.
17. Canonical names across the family (round 1, F-019, DEC-017): required status check `ci-gate` (the only required check); environments `<env>` (deploy: write role, also used by the merge-time Terraform plan that must take the state lock) and `<env>-pr` (PR read-only role, Terraform PR plan with `-lock=false`); AWS role ARN variables `AWS_PR_ROLE_ARN` (in `<env>-pr`), `AWS_DEPLOY_ROLE_ARN` (in `<env>`) and, for the image publish stage only, `ECR_PUSH_ROLE_ARN` (push-only role in `<env>-publish`; round 2, F-034), read inside the called job that declares the environment, never in the caller; reusable image workflow `_image-publish.yml` with outputs `digest` and `image-ref` (`image-ref` already contains `@sha256:`); block inputs exactly as the owning skill defines them (composing's catalog copies them, never invents).
18. Every job sets `timeout-minutes`; every caller has a `concurrency` group (PR: cancel-in-progress true; deploy: per app and environment, cancel-in-progress false); `id-token: write` only on the job that logs in; a reusable workflow that uses `environment:` reads that environment's secrets/variables directly and does not declare them as required `workflow_call` secrets (round 1, F-016, F-020, F-021).
