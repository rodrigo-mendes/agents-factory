## Module Types & When to Use

| Type | Purpose | Scope | Example |
|------|---------|-------|---------|
| **Resource module** | Thin wrapper around 1-3 OCI resources | Single concern only | `modules/vcn` (VCN + subnets + gateways) |
| **Infrastructure module** | Composes multiple resource modules into a layer | Cross-concern stack | `modules/networking-stack` (VCN + NSGs + DRG) |
| **Composition/root module** | Environment-specific config calling infra modules | Full environment | `environments/prod/main.tf` |
| **Utility module** | Data transformations, naming, tagging | No resources created | `modules/naming-convention` |

### Anti-Pattern: God Module
Never create a single module that provisions everything (networking, compute, IAM, storage). Split by logical concern for independent blast radius.

## Standard Module Structure

Every module directory MUST contain:

```
modules/vcn/
├── main.tf           # Resources and data sources
├── variables.tf      # All input variables (alphabetical)
├── outputs.tf        # All outputs (alphabetical)
├── README.md         # Auto-generated by terraform-docs
└── versions.tf       # (optional) terraform {} block if module has own constraints
```

## Interface Design Rules

### Variable Rules
- Every variable MUST have `type`, `description`, and `validation` (where applicable)
- Follow ordering convention: `type` → `description` → `default` → `sensitive` → `validation`
- Validate OCIDs with `can(regex("^ocid1\\.", var.name))` pattern
- Validate CIDRs with `can(cidrhost(cidr, 0))` pattern
- Include `freeform_tags` and `defined_tags` variables with `default = {}` for all modules

### Output Rules
- Output names MUST be snake_case and match the resource attribute
- Every output MUST have a `description`
- Sensitive outputs MUST be marked `sensitive = true`

### README Auto-Generation
Use `terraform-docs` to auto-generate `README.md`: `terraform-docs markdown table . > README.md`

## Module Sources & Versioning

### Current Strategy: Local Paths
For solo developer, use local module paths: `source = "../../modules/networking"`

### Future Migration: Git Tags
When the project grows, migrate to Git-referenced modules with pessimistic version constraints (`~> 1.2`)

## Composition Patterns

### Flat Composition (Recommended)
Root modules call all modules at the same level — no deep nesting. Pass values between modules using outputs and variables (dependency injection).

### Cross-Module References
- Pass values via outputs and variables — explicit dependency injection
- NEVER use `terraform_remote_state` — creates tight coupling, exposes all outputs

## Module Design Anti-Patterns
- 🚫 **God module**: Single module provisioning everything
- 🚫 **Leaky abstraction**: Module exposing internal resource details that shouldn't be public
- 🚫 **Missing validation**: Variables without type constraints or validation blocks
- 🚫 **Undocumented module**: No README.md or variable descriptions
- 🚫 **Resource type in name**: `resource "oci_core_vcn" "oci_core_vcn_main" {}` — use descriptive noun instead
