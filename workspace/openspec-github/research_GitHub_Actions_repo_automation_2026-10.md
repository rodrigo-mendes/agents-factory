## Executive Summary

GitHub Actions runs workflows in response to repository events. For this family the relevant triggers are
`issue_comment` (approval commands written as comments on issues/PRs), `issues` with `labeled`
(label-driven gates), `pull_request` (CI checks that gate merges) and `push` with `branches`/`paths`
filters (sync after merge). `issue_comment` and `issues` always run the workflow file **from the default
branch** with `GITHUB_SHA` = last commit on the default branch, and only trigger if the workflow file
exists on the default branch. A workflow that writes to a GitHub Project v2 cannot use `GITHUB_TOKEN`
("scoped to the repository level and cannot access projects", F2); it needs a GitHub App installation
token (organization projects) generated with `actions/create-github-app-token@v3`, or a classic PAT with
`project` + `repo` scopes (user projects, F3/F6), stored as a secret.

What changed recently and matters for skill authors: (1) `actions/create-github-app-token` v3 moved to
Node 24 (v3.0.0, 2026-03-14, needs runner v2.327.1+ on self-hosted), added `client-id` and deprecated
`app-id` (v3.1.0, 2026-04-11), added enterprise apps and `owner/repo` entries in `repositories`
(v3.2.0) and refreshed the `permission-*` inputs (v3.3.0, 2026-10-12). (2) `actions/checkout` v7
(2026-06-18) refuses to check out fork PR code in `pull_request_target` and `workflow_run`
(pull_request*) workflows unless `allow-unsafe-pr-checkout: true`; this was backported to the floating
`v3`-`v6` tags on 2026-07-20. (3) "Workflow dependency lockfiles" (`.github/workflows/actions.lock`,
generated by the `gh actions-lock` extension) entered **public preview** on 2026-10-14 and GitHub's
secure-use reference now says it "supersedes SHA pinning for repositories that adopt it".

Three critical patterns: **never interpolate `${{ github.event.* }}` text into `run:`** (pass it via
`env:` and quote `"$VAR"`); **declare least-privilege `permissions:`** (an explicit block sets every
unlisted scope to `none`) and **pin actions to full commit SHAs**; **guard against loops and concurrent
runs** (bot-author `if:` guards, per-issue `concurrency` groups, `timeout-minutes`), because events created
with an App token or PAT are not subject to the `GITHUB_TOKEN` no-new-run rule. Tier: **Complex** —
credentials with org-wide reach, supply-chain and injection risks, and cross-workflow triggering.

### ✅ Mandatory Patterns

**A1. Pass untrusted event text to scripts through `env:`, never inline `${{ }}`**
> Confidence: 🟢 High | [✓✓ Triangulated | secure-use reference (2026-10-29) + script-injections concept (2026-10-29)]
- Why: "the expressions inside `${{ }}` are evaluated and then substituted with the resulting values" before the shell runs, so a PR title such as `a"; ls $GITHUB_WORKSPACE"` executes. Untrusted fields "typically end with `body`, `default_branch`, `email`, `head_ref`, `label`, `message`, `name`, `page_name`, `ref`, and `title`." Applies to `github.event.comment.body`, `github.event.issue.title`, `github.event.label.name`.
- Code (GitHub.com, Actions 2026-10):
  ```yaml
  - name: Parse approval command
    env:
      COMMENT_BODY: ${{ github.event.comment.body }}
      ISSUE_NUMBER: ${{ github.event.issue.number }}
    run: |
      python3 .github/scripts/parse_command.py --issue "$ISSUE_NUMBER" --body-env COMMENT_BODY
  ```
- Source: https://docs.github.com/en/actions/reference/security/secure-use (2026-10-29); https://docs.github.com/en/actions/concepts/security/script-injections (2026-10-29)

**A2. Declare explicit least-privilege `permissions:` (workflow default read-only, raise per job)**
> Confidence: 🟢 High | [✓✓ Triangulated | secure-use reference + workflow-syntax reference (2026-10-29)]
- Why: "set the default permission for the `GITHUB_TOKEN` to read access only for repository contents ... The permissions can then be increased, as required, for individual jobs". "If you specify the access for any of these permissions, all of those that are not specified are set to `none`." `permissions: {}` disables all.
- Code:
  ```yaml
  permissions:
    contents: read          # workflow default
  jobs:
    sync:
      permissions:
        contents: read
        issues: write        # only if this job comments with GITHUB_TOKEN
  ```
- Source: https://docs.github.com/en/actions/reference/security/secure-use (2026-10-29); https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax (2026-10-29, partly read in 3 chunks)

**A3. Pin every action to a full-length commit SHA (with the version in a comment)**
> Confidence: 🟢 High | [✓✓ Triangulated | secure-use reference + repository Actions settings page (2026-10-29)]
- Why: "Pin references to actions to a commit SHA in your workflow files"; verify the SHA "is from the action's repository and not a repository fork". The repository setting "Require actions to be pinned to a full-length commit SHA" applies to all actions **including GitHub-authored ones** (so pin `actions/*` too, not only third-party). Note: "Dependabot only creates alerts for vulnerable actions that use semantic versioning", so SHA pinning needs Dependabot version updates to stay current.
- Code (SHAs resolved 2026-10-29 via `api.github.com/repos/<repo>/git/ref/tags/<tag>`, prefixes match the releases pages):
  ```yaml
  - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1                 # v7.0.1
  - uses: actions/create-github-app-token@64ab729a6294000f5aa4a4bc0b73d1f32bc45510  # v3.3.0
  - uses: actions/setup-python@6d4fd22b20465ccc0f7354476588e8df7c9ca0e0             # v7.1.0
  ```
- Source: https://docs.github.com/en/actions/reference/security/secure-use (2026-10-29); https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository (2026-10-29); release pages in Bibliography.

**A4. Use a GitHub App installation token (org projects) or classic PAT secret (user projects) for Projects v2 — never `GITHUB_TOKEN`**
> Confidence: 🟢 High | [✓✓ Triangulated | automating-projects-using-actions (2026-10-29) + create-github-app-token README/action.yml (2026-10-29)] — consistent with F2, F3, F6, rule 5
- Why: "`GITHUB_TOKEN` is scoped to the repository level and cannot access projects." App: "read and write permissions to organization projects" plus "read permissions to repository pull requests and repository issues". User projects: "personal access token (classic) with the `project` and `repo` scopes". Docs use variable `APP_CLIENT_ID`, secret `APP_PRIVATE_KEY`, PAT secret placeholder `YOUR_TOKEN`.
- Code:
  ```yaml
  - id: app-token
    uses: actions/create-github-app-token@64ab729a6294000f5aa4a4bc0b73d1f32bc45510  # v3.3.0
    with:
      client-id: ${{ vars.APP_CLIENT_ID }}          # app-id is deprecated since v3.1.0
      private-key: ${{ secrets.APP_PRIVATE_KEY }}
      owner: ${{ github.repository_owner }}
      permission-organization-projects: write
      permission-issues: write
  - run: gh project item-list "$PROJECT_NUMBER" --owner "$OWNER" --format json
    env:
      GH_TOKEN: ${{ steps.app-token.outputs.token }}   # user projects: ${{ secrets.YOUR_TOKEN }}
      OWNER: ${{ github.repository_owner }}
      PROJECT_NUMBER: ${{ vars.PROJECT_NUMBER }}
  ```
- Source: https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/automating-projects-using-actions (2026-10-29); https://github.com/actions/create-github-app-token (2026-10-29); https://github.com/actions/create-github-app-token/blob/main/action.yml (2026-10-29)

**A5. Mint the App token in the job that uses it; down-scope with `repositories` and `permission-*`**
> Confidence: 🟢 High | [✓✓ Triangulated | create-github-app-token README + installation-token docs (2026-10-29)]
- Why: "By default, the token inherits all of the installation's permissions"; the token "cannot be granted permissions that the app was not granted". "An installation access token expires after 1 hour." "Unless the `skip-token-revoke` input is set to true, the token is revoked in the `post` step of the action, which means it cannot be passed to another job." Valid `permission-*` names include `permission-organization-projects` (`read`|`write`|`admin`), `permission-repository-projects`, `permission-issues`, `permission-pull-requests`, `permission-contents`, `permission-workflows` (write only).
- Code: see A4 (one `create-github-app-token` step per job; `repositories: ${{ github.event.repository.name }}` to restrict to the current repo).
- Source: https://github.com/actions/create-github-app-token (2026-10-29); https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app (2026-10-29)

**A6. Distinguish issue vs PR comments with `github.event.issue.pull_request`**
> Confidence: 🟡 Medium (single official page, read in full section)
- Why: "The `issue_comment` event occurs for comments on both issues and pull requests." Official example uses `if: ${{ github.event.issue.pull_request }}` (PR) and `if: ${{ !github.event.issue.pull_request }}` (issue). Expressions starting with `!` must be wrapped in `${{ }}` because "`!` is reserved notation in YAML format".
- Code:
  ```yaml
  on:
    issue_comment:
      types: [created, edited]
  jobs:
    approve:
      if: ${{ !github.event.issue.pull_request }}
  ```
- Source: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows (2026-10-29); workflow-syntax (2026-10-29)

**A7. Serialize per issue/change with `concurrency` and bound runtime with `timeout-minutes`**
> Confidence: 🟢 High | [✓✓ Triangulated | workflow-syntax + control-workflow-concurrency how-to (2026-10-29)]
- Why: "there can be at most one running job or workflow in a concurrency group at any time"; with default `queue: single`, an existing pending run in the group "is canceled and replaced"; `cancel-in-progress: true` also cancels the running one; `queue: max` (up to 100 pending) cannot be combined with `cancel-in-progress: true`. Job `timeout-minutes` "Default: 360". Group names are case insensitive.
- Code:
  ```yaml
  concurrency:
    group: openspec-sync-${{ github.event.issue.number }}
    cancel-in-progress: false     # approvals must not be dropped mid-write
  jobs:
    sync:
      timeout-minutes: 10
  ```
- Source: https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax (2026-10-29); https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency (2026-10-29). Note: per-issue group key `github.event.issue.number` is not shown in an official example (medium confidence on the exact expression; the mechanism is High).

**A8. Set `GH_TOKEN` explicitly for every `gh` step**
> Confidence: 🟢 High | [✓✓ Triangulated | use-github-cli how-to + automating-projects page (2026-10-29)]
- Why: "GitHub CLI is preinstalled on all GitHub-hosted runners" and "you must set an environment variable called `GH_TOKEN` to a token with the required scopes."
- Code: see A4.
- Source: https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-github-cli (2026-10-29)

**A9. Authenticate an `issue_comment` approval by `author_association` and reject bot authors**
> Confidence: 🟡 Medium (enum High from REST schema; `user.type == 'Bot'` value (unverified))
- Why: comment `author_association` enum: `COLLABORATOR`, `CONTRIBUTOR`, `FIRST_TIMER`, `FIRST_TIME_CONTRIBUTOR`, `MANNEQUIN`, `MEMBER`, `NONE`, `OWNER`. Anyone who can comment on a public issue triggers `issue_comment`, so the workflow must check who commented. Fields `comment.id` (int64), `comment.html_url`, `comment.created_at` (date-time) are required in the schema.
- Code:
  ```yaml
  if: >-
    ${{ !github.event.issue.pull_request &&
        contains(fromJSON('["OWNER","MEMBER","COLLABORATOR"]'), github.event.comment.author_association) &&
        github.event.comment.user.type != 'Bot' }}
  ```
- Source: https://docs.github.com/en/rest/issues/comments (2026-10-29). `user.type` is documented only as "required, string" (unverified value set).

### ⚠️ Conditional Patterns

**C1. Credential type: GitHub App vs classic PAT**
> Confidence: 🟢 High (F3, F6, rule 5, rule 10)
- Options: A) GitHub App installation token; B) classic PAT `project` + `repo`.
- Tradeoffs:

  | Option | Optimizes | Sacrifices | Best When |
  |--------|-----------|------------|-----------|
  | App | 1-hour tokens, per-job down-scoping, org-owned identity `<slug>[bot]` | App registration + install + private key secret | `tracker.owner_type: organization` |
  | Classic PAT | Only option for user-owned projects (F6) | Broad `repo` scope, tied to a person, manual rotation | `tracker.owner_type: user` (print risk warning, rule 10) |

- Agent: "Ask user whether the project is owned by an organization or a user account."
- Source: automating-projects-using-actions (2026-10-29); F6.

**C2. How to push a branch and open a PR from a workflow**
> Confidence: 🟡 Medium
- Options: A) App token + `gh auth setup-git` + `git push` + `gh pr create` (README pattern); B) `actions/checkout` with `token: <app token>`; C) `GITHUB_TOKEN` (needs repo setting "Allow GitHub Actions to create and approve pull requests", off by default for personal repos; PR CI runs land in approval-required state).
- Tradeoffs:

  | Option | Optimizes | Sacrifices | Best When |
  |--------|-----------|------------|-----------|
  | A | Commits/PR authored by `<slug>[bot]`; PR CI runs normally | Requires `contents: write` + `pull-requests: write` on the App (medium confidence) | Default for this family |
  | B | Simple; checkout persists the token (`persist-credentials` default `true`) | Token stays in `.git/config` for later steps | Single-job push |
  | C | No extra credential | No Projects access (F2); PR runs "approval-required" | Never for this family |

- Agent: "Ask whether the generated PR must trigger required CI checks automatically (then A or B)."
- Source: https://github.com/actions/create-github-app-token (2026-10-29); https://github.com/actions/checkout (2026-10-29); https://docs.github.com/en/actions/concepts/security/github_token (2026-10-29); repo Actions settings page (2026-10-29).

**C3. `cancel-in-progress` true vs false**
> Confidence: 🟢 High
- Options: true (latest wins) / false (queue; one pending replaced).
- Tradeoffs:

  | Option | Optimizes | Sacrifices | Best When |
  |--------|-----------|------------|-----------|
  | true | Fast feedback on CI | Can abort a half-done multi-step write | PR CI workflows |
  | false | Writes finish | Intermediate pending runs are replaced (only the newest pending survives) | Sync/approval writers |

- Source: workflow-syntax; control-workflow-concurrency (2026-10-29).

**C4. Required status checks with path-filtered CI**
> Confidence: 🟢 High
- Options: A) no path filter on required workflow; B) path filter + always-succeeding companion workflow with same check name; C) job-level `if:` skip.
- Tradeoffs: a workflow skipped by path/branch filter or commit message leaves checks "Pending" and blocks merging; a job skipped by a conditional "reports "Success"". "Avoid requiring workflows that can be skipped."
- Source: https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks (2026-10-29); https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets (2026-10-29)

**C5. Workflow dependency lockfile vs SHA pinning**
> Confidence: 🟡 Medium (public preview since 2026-10-14)
- Options: SHA pinning (GA practice) / `.github/workflows/actions.lock` via `gh actions-lock` (preview; Free, Team, Enterprise Cloud).
- Agent: "Ask whether the repository opts into the lockfile preview; default to SHA pinning (rule 8)."
- Source: https://github.blog/changelog/2026-10-14-github-actions-workflow-lockfiles-in-public-preview/ (2026-10-29); secure-use reference (2026-10-29)

**C6. Runner image pin: `ubuntu-latest` vs `ubuntu-24.04`**
> Confidence: 🟢 High
- `ubuntu-latest` = Ubuntu 24.04 today; `-latest` migration "is gradual and happens over 1-2 months"; images update weekly (gh version changes weekly). Pin `ubuntu-24.04` to avoid surprise migrations; run a `gh --version` preflight (rule 9).
- Source: https://github.com/actions/runner-images (2026-10-29)

### 🚫 Forbidden Patterns

**N1. Inline `${{ github.event.* }}` text in `run:`**
> Severity: Critical
> Confidence: 🟢 High
- Why: expression is substituted into the script before execution.
- Impact: arbitrary command execution with the job's token and secrets.
- ❌ Wrong:
  ```yaml
  run: echo "${{ github.event.comment.body }}" | python3 parse.py
  ```
- ✅ Correct:
  ```yaml
  env:
    COMMENT_BODY: ${{ github.event.comment.body }}
  run: printf '%s' "$COMMENT_BODY" | python3 parse.py
  ```
- Source: secure-use reference; script-injections concept (2026-10-29)

**N2. Using `GITHUB_TOKEN` for Projects v2**
> Severity: High
> Confidence: 🟢 High
- Why/Impact: "cannot access projects" — GraphQL calls fail.
- ❌ Wrong:
  ```yaml
  env: { GH_TOKEN: "${{ secrets.GITHUB_TOKEN }}" }
  run: gh project item-edit ...
  ```
- ✅ Correct:
  ```yaml
  env: { GH_TOKEN: "${{ steps.app-token.outputs.token }}" }
  run: gh project item-edit ...
  ```
- Source: automating-projects-using-actions (2026-10-29)

**N3. `pull_request_target` that checks out / runs PR code**
> Severity: Critical
> Confidence: 🟢 High
- Why: runs "in the context of the default branch of the base repository" with secrets; "Avoid using this event if you need to build or run code from the pull request"; such vulnerabilities "can be exploited to take over a repository". checkout v7 blocks fork-PR checkout here unless `allow-unsafe-pr-checkout: true`.
- ❌ Wrong:
  ```yaml
  on: pull_request_target
  steps:
    - uses: actions/checkout@<sha>
      with: { ref: "${{ github.event.pull_request.head.sha }}", allow-unsafe-pr-checkout: true }
    - run: make test
  ```
- ✅ Correct:
  ```yaml
  on: pull_request          # fork PRs get read-only GITHUB_TOKEN and no secrets
  permissions: { contents: read }
  ```
- Source: events-that-trigger-workflows; secure-use; checkout README; github.blog changelog 2026-06-18 (all 2026-10-29)

**N4. Mutable tag refs (`@v3`, `@main`) in hardened workflows**
> Severity: High
> Confidence: 🟢 High
- Why: tags/branches can move after review; "Pin actions to a tag only if you trust the creator." Floating major tags also silently pick up behaviour changes (checkout v4-v6 backport of 2026-07-20).
- ❌ Wrong: `uses: actions/create-github-app-token@v3`
- ✅ Correct: `uses: actions/create-github-app-token@64ab729a6294000f5aa4a4bc0b73d1f32bc45510  # v3.3.0`
- Source: secure-use reference; github.blog changelog 2026-06-18 (2026-10-29)

**N5. Writer workflow with no loop guard when acting with an App token or PAT**
> Severity: High
> Confidence: 🟡 Medium (mechanism partly inferred, see Gap G2)
- Why: only `GITHUB_TOKEN`-created events are exempt from creating runs ("events triggered by the `GITHUB_TOKEN` will not create a new workflow run"); docs direct you to App/PAT tokens precisely to get runs on created PRs, so App/PAT-made comments/labels can retrigger the same workflow.
- Impact: comment/label storms, rate-limit exhaustion, duplicate Project writes.
- ❌ Wrong:
  ```yaml
  on: { issue_comment: { types: [created] } }
  jobs: { reply: { runs-on: ubuntu-24.04, steps: [ { run: "gh issue comment ..." } ] } }
  ```
- ✅ Correct:
  ```yaml
  jobs:
    reply:
      if: ${{ github.event.comment.user.type != 'Bot' && github.event.comment.user.login != 'my-app[bot]' }}
      concurrency: { group: "reply-${{ github.event.issue.number }}", cancel-in-progress: false }
  ```
- Source: https://docs.github.com/en/actions/concepts/security/github_token (2026-10-29); events-that-trigger-workflows (2026-10-29)

**N6. Secrets/plaintext credentials or structured secrets in workflow files**
> Severity: Critical
> Confidence: 🟢 High
- Why: "Sensitive data should **never** be stored as plaintext in workflow files"; "Never use structured data as a secret" (redaction is exact-match); "Any user with write access to your repository has read access to all secrets".
- ❌ Wrong: `GH_TOKEN: ghp_xxxxxxxx` or one JSON secret holding client id + key.
- ✅ Correct: `client-id: ${{ vars.APP_CLIENT_ID }}` + `private-key: ${{ secrets.APP_PRIVATE_KEY }}`.
- Source: secure-use reference (2026-10-29)

**N7. Path/branch filters on a workflow that is a required status check**
> Severity: Medium
> Confidence: 🟢 High
- ❌ Wrong: required check `ci` from a workflow with `on: pull_request: paths: ['src/**']` (docs-only PR stays "Pending", unmergeable).
- ✅ Correct: no path filter on the workflow; skip expensive jobs with job-level `if:` (skipped job "reports "Success"").
- Source: troubleshooting-required-status-checks (2026-10-29)

## Migration Guide

> Confidence: 🟢 High | Sources: create-github-app-token releases (2026-10-29) + checkout releases + github.blog changelog 2026-06-18 (2026-10-29)

**Breaking Changes**:
- `create-github-app-token` v3.0.0 (2026-03-14): Node 24 runtime; custom proxy handling removed (proxy users must set `NODE_USE_ENV_PROXY=1` on the step); self-hosted runners need Actions Runner v2.327.1+.
- `create-github-app-token` v3.1.0 (2026-04-11): `client-id` input added, `app-id` **deprecated** ("Use 'client-id' instead"; still accepted). ⚠️ Migration Note: any pattern using `app-id:` must move to `client-id:` (docs now use `vars.APP_CLIENT_ID`).
- `create-github-app-token` v3.2.0 (2026-05-12): `enterprise` input (mutually exclusive with `owner`/`repositories`); `repositories` accepts `owner/repo`; private-key validation.
- `create-github-app-token` v3.3.0 (2026-10-12): permission inputs updated (#399).
- `checkout` v7.0.0 (2026-06-18): refuses fork PR checkout under `pull_request_target`, and `workflow_run` when `workflow_run.event` is `pull_request*`; opt-out `allow-unsafe-pr-checkout` (default `false`); module moved to ESM. Backported as v6.1.0 / v5.1.0 / v4.4.0 / v3.7.0 (marked [BREAKING]) to floating majors on 2026-07-20; v1 excluded; SHA/minor/patch pins unaffected.
- `setup-python` v7.0.0 (2026-07-20): `pip-install` input removed (not labelled breaking by the release notes; inference).

## Implementation Blueprint

> Confidence: 🟢 High | [✓✓ Triangulated | official README examples + official docs] — loop guard and App permission set: (medium confidence)

**Lifecycle** — approval comment → Project update (organization project, App token):
```yaml
# .github/workflows/approval-comment.yml — GitHub.com, create-github-app-token v3.3.0, checkout v7.0.1
name: approval-comment
on:
  issue_comment:
    types: [created, edited]      # runs the default-branch copy of this file; GITHUB_SHA = default-branch tip
permissions: {}                   # nothing from GITHUB_TOKEN unless a job asks
concurrency:
  group: approval-${{ github.event.issue.number }}
  cancel-in-progress: false
jobs:
  approve:
    if: >-
      ${{ !github.event.issue.pull_request &&
          contains(fromJSON('["OWNER","MEMBER","COLLABORATOR"]'), github.event.comment.author_association) &&
          github.event.comment.user.type != 'Bot' }}
    runs-on: ubuntu-24.04
    timeout-minutes: 10
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1   # v7.0.1
        with:
          persist-credentials: false
      - uses: actions/setup-python@6d4fd22b20465ccc0f7354476588e8df7c9ca0e0  # v7.1.0
        with:
          python-version: '3.12'
      - id: app-token
        uses: actions/create-github-app-token@64ab729a6294000f5aa4a4bc0b73d1f32bc45510  # v3.3.0
        with:
          client-id: ${{ vars.APP_CLIENT_ID }}
          private-key: ${{ secrets.APP_PRIVATE_KEY }}
          repositories: ${{ github.event.repository.name }}
          permission-organization-projects: write
          permission-issues: write
      - name: Record approval
        env:
          GH_TOKEN: ${{ steps.app-token.outputs.token }}
          COMMENT_BODY: ${{ github.event.comment.body }}
          COMMENT_ID: ${{ github.event.comment.id }}
          COMMENT_URL: ${{ github.event.comment.html_url }}
          COMMENT_AT: ${{ github.event.comment.created_at }}
          ISSUE_NUMBER: ${{ github.event.issue.number }}
        run: |
          gh --version
          python3 .github/scripts/record_approval.py   # reads the values from env, never from argv text
```

**Integration**: Actions ↔ git/gh — open a PR as the App bot (README "Configure Git CLI" pattern):
```yaml
      - id: app-token
        uses: actions/create-github-app-token@64ab729a6294000f5aa4a4bc0b73d1f32bc45510  # v3.3.0
        with:
          client-id: ${{ vars.APP_CLIENT_ID }}
          private-key: ${{ secrets.APP_PRIVATE_KEY }}
          repositories: ${{ github.event.repository.name }}
          permission-contents: write          # push branch (medium confidence on exact set)
          permission-pull-requests: write     # gh pr create (medium confidence)
      - name: Push branch and open PR
        env:
          GH_TOKEN: ${{ steps.app-token.outputs.token }}
          APP_SLUG: ${{ steps.app-token.outputs.app-slug }}
          BRANCH: openspec/sync-${{ github.run_id }}
        run: |
          BOT_ID=$(gh api "/users/${APP_SLUG}[bot]" --jq .id)
          git config user.name  "${APP_SLUG}[bot]"
          git config user.email "${BOT_ID}+${APP_SLUG}[bot]@users.noreply.github.com"
          gh auth setup-git
          git switch -c "$BRANCH"
          git commit -am "chore(openspec): sync from approvals"
          git push origin "$BRANCH"
          gh pr create --head "$BRANCH" --title "OpenSpec sync" --body "Automated by ${APP_SLUG}[bot]"
```
Note: pushing changes under `.github/workflows/` also needs `permission-workflows: write` (input exists, write-only) (medium confidence that it is required for push).

## Production Readiness

- **Performance**: job default timeout 360 min — always set `timeout-minutes`; App token lives 1 hour, so long jobs must re-mint.
- **Scalability**: concurrency `queue: single` keeps only the newest pending run per group; `queue: max` allows 100 pending. `push` events are not created if more than 5,000 branches are pushed at once.
- **Monitoring**: log `gh --version` (image updates weekly), comment id/url for audit; Dependabot alerts do not cover SHA-pinned actions — enable version updates.
- **Security**:
  - [ ] `permissions:` explicit; workflow default read-only or `{}`
  - [ ] all actions SHA-pinned (incl. `actions/*`) or lockfile adopted
  - [ ] no `${{ github.event.* }}` in `run:`
  - [ ] `author_association` + bot guard on comment/label triggers
  - [ ] App token per job, down-scoped (`repositories`, `permission-*`)
  - [ ] no `pull_request_target` with PR code; no `allow-unsafe-pr-checkout: true`
  - [ ] fork PRs: secrets (except `GITHUB_TOKEN`) not passed, `GITHUB_TOKEN` read-only; Dependabot PRs treated as forks
  - [ ] classic PAT only for user projects, with risk warning (rule 10); rotate secrets periodically
  - [ ] `issue_comment`/`issues` workflows changes take effect only after merge to default branch
