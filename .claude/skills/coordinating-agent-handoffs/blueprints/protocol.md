## Why records

Every transition between agents passes context through a **structured record file**, never through
conversation history or lossy prose. The receiving agent reads the record and the `refs` it
points to and skips re-analysis of anything already recorded. Records are the source of truth;
only the invocation mechanism differs per tool.

## Layout

```
<root>/                      root comes from the profile, e.g. openspec/changes/<id>/handoff
  wo-01-code.md              work-order   (orchestrator -> agent)
  result-01-code.md          report       (agent -> orchestrator)
  review-01.md               review       (reviewer -> orchestrator)
  deploy-report.md           deploy-report
  diagnosis-report.md        diagnosis-report
  spec-delta-01.md           spec-delta   (spec-synchronizer -> orchestrator/user)
  escalation-01.md           escalation   (orchestrator -> user)
  verify-E3.md               verify       (independent verifier)
  status.md                  status       (GENERATED by board.py)
```

File names follow the profile's `records:` patterns; the scripts classify a file by its `kind:`
frontmatter, not by its name (a profile may map legacy names with `kind_overrides`).
`detect_drift.py` additionally keeps a name-based classification of files by legacy name prefix
as a backward-compatibility fallback for records without `kind`; new records always carry `kind`.
Records are append-only within a cycle: a new attempt is a new record with the next `nn`.
A profile may declare that a family overwrites records per cycle (OCI legacy); then counters that
depend on history (limits) are not meaningful for that family.

## Modes

| | user-mediated | orchestrated |
|---|---|---|
| Who runs the next step | the user, told which command to run | the orchestrator, from `board.py` |
| Chaining | none; each agent ends with a hand-off line | orchestrator launches agents; agents never launch agents |
| Approvals | the user decides every step | the user approves only the gates the profile names |
| `status.md` | optional | required (counters, limits, next action) |
| Typical family | OCI | Quarkus/AWS SaaS |

The records are identical in both modes.

## Handshake (every step)

1. **Intake.** The orchestrator (or the user) writes a work-order and runs
   `check_records.py`. The agent reads the work-order, its `refs`, and the skills the work-order
   lists. It does not read the conversation history.
2. **Work.** The agent works and writes **one** output record from the template.
3. **Close.** The agent states the outcome and the single next action and points at the record.
   Single phrasing in user-mediated mode:

   > **Hand off:** run `/<command>` (`@<agent>`) - `<one-line why>`. Context: `<root>/<record>.md`

4. **Verify.** The orchestrator runs `check_records.py` (exit != 0: return the list of errors to
   the agent), then `detect_drift.py` (exit 2: pass `drift=true` to the board), then `board.py`.
   `detect_drift.py` exits 1 when `status.md` has no `lastSyncedSha`: run it only for families with
   `spec.kind: openspec` after the baseline `board.py --sync-sha <sha>` was recorded; `spec.kind: none`
   families (OCI) skip it, and before the baseline exit 1 is expected, never read as "no drift".
5. **Decide.** `board.py` evaluates the profile's `next` rules and prints `NEXT: ...`.
   Orchestrator mode: follow it. User-mediated mode: tell the user which command to run.

## Rules

1. An agent writes exactly one output record per invocation and never edits another agent's record,
   except the orchestrator updating a work-order `status`.
2. **The producer never verifies its own work.** The `verify` that gates a stage must come from an
   agent other than the producer of that stage: its `from` differs from the author of every ref
   (enforced by `check_records.py`).
3. Only the orchestrator talks to the user; agents return `outcome: needs-input` and put the
   question in the record. Nobody except the user's own message approves a gate.
4. Reports always carry **Spec impact** (even "none"), so drift has a first, cheap detection point.
5. Every loop has a limit ([limits](./profile-format.md#limits-and-parameters)); reaching it
   produces an `escalation`, never a silent retry.
6. Records and `status.md` are committed with the code; archiving a change moves the folder whole.

## Escalation

Triggered when `board.py` reports `NEXT: escalate ...`. The orchestrator stops the affected task
(independent tasks continue), writes an `escalation` record (attempts, evidence, hypothesis, 2-4
options) and shows it to the user. The user's reply is recorded **verbatim** under `## Answer`,
the record is set to `status: answered` with `answeredAt`, and the counters of that task restart
from the answer time. No new apply/deploy happens on an open escalation.

## Per-tool mechanism

| Step | Claude Code | Other tools |
|---|---|---|
| Intake / write | Read / Write tools | file read/write of the same records |
| Programmatic launch (orchestrated) | `Agent` tool, orchestrator only | not available: user-mediated |
| User-mediated hand-off | prose line "run `/cmd`" | same prose line |
| Scripts | `python scripts/<name>.py` (Python 3.8+ (unverified, U1), stdlib only) | same |

## Worked flow (orchestrated)

```
wo-01-code (done) -> result-01-code success -> check_records OK -> board: NEXT role=reviewer
review-01 approved -> orchestrator marks wo-01-code done -> board: all tasks done -> NEXT deploy
deploy-report success -> board: NEXT observability -> observability result (kind report)
-> independent verify (role debug in the Quarkus profile; verify-E7 pass)
detect_drift exit 0, board: drift=false, pending_deltas=0 -> NEXT: final-gate
```
