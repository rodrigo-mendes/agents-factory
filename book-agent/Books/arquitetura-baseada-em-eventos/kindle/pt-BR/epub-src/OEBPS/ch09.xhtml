Capítulo 9: Observabilidade, Depuração e Operações

Declaração do Problema Inicial

Um cliente reclama que um pedido foi cobrado duas vezes, mas o e-mail de confirmação nunca chegou. Em um sistema síncrono, você abriria um stack trace e seguiria a cadeia de chamadas do início ao fim. Em um sistema orientado a eventos, não há stack trace. O serviço de pagamento publicou um fato. Três consumidores reagiram de forma independente. Esta é a dor operacional central da EDA: o fluxo de controle é implícito. Nenhum serviço isolado conhece a história completa, porque o desacoplamento oculta a cadeia causal.

Rastreamento Distribuído e IDs de Correlação/Causalidade

Um correlation ID é um identificador único compartilhado por todo evento que pertence à mesma transação de negócio lógica. Ele é gerado uma única vez, na borda, e copiado sem alteração para cada evento resultante. Um causation ID responde a uma pergunta mais específica: qual evento específico causou diretamente este? O causation ID de cada evento é o message ID de seu pai imediato.

A regra é simples e absoluta: todo consumidor que produz um novo evento copia o correlation ID e define o causation ID como o ID do evento pai. Esquecer isso em um único consumidor e a cadeia se rompe ali.

# Message envelope with traceability fields and child-event construction pattern
from __future__ import annotations

import uuid
from dataclasses import dataclass, field
from datetime import datetime, timezone


@dataclass(frozen=True)
class EventEnvelope:
    """Immutable wrapper carried by every event through the system."""
    message_id: str
    event_type: str
    event_version: str
    payload: dict
    correlation_id: str
    causation_id: str
    timestamp: str = field(
        default_factory=lambda: datetime.now(timezone.utc).isoformat()
    )

    @staticmethod
    def create_root(event_type: str, event_version: str, payload: dict) -> "EventEnvelope":
        """Create the first event in a flow; its own ID seeds the correlation chain."""
        new_id = str(uuid.uuid4())
        return EventEnvelope(
            message_id=new_id,
            event_type=event_type,
            event_version=event_version,
            payload=payload,
            correlation_id=new_id,
            causation_id=new_id,
        )

    def spawn_child(self, event_type: str, event_version: str, payload: dict) -> "EventEnvelope":
        """Produce a child event: copy correlation_id, set causation_id to this event's ID."""
        return EventEnvelope(
            message_id=str(uuid.uuid4()),
            event_type=event_type,
            event_version=event_version,
            payload=payload,
            correlation_id=self.correlation_id,
            causation_id=self.message_id,
        )


def handle_order_placed(parent: EventEnvelope, publisher) -> None:
    """
    Payment consumer: receives OrderPlaced, performs capture, emits PaymentCaptured.
    Demonstrates the mandatory ID-propagation rule.
    """
    order_id = parent.payload["order_id"]
    amount = parent.payload["amount"]
    charge_result = {"charge_id": "ch_abc123", "status": "captured"}

    child_event = parent.spawn_child(
        event_type="payment.captured",
        event_version="1.0",
        payload={
            "order_id": order_id,
            "amount": amount,
            "charge_id": charge_result["charge_id"],
        },
    )
    publisher.publish(topic="payments", event=child_event)

💡 Nota do Especialista: O texto recomenda corretamente vincular spans assíncronos por meio de span links do OpenTelemetry, mas na prática a maioria dos backends de observabilidade — Jaeger, Zipkin e até algumas configurações do agente Datadog — tem suporte parcial ou inconsistente para span links. Equipes que dependem de span links frequentemente descobrem que seus traces são renderizados como fragmentos desconectados na interface.
💡 Nota do Especialista Um erro comum na camada do API gateway é reutilizar o header HTTP de entrada X-Request-ID diretamente como correlation ID. Esses headers são gerados por load balancers em formatos que variam entre fornecedores. Melhor prática: sempre gere um UUID v4 novo na fronteira do domínio e use-o exclusivamente como correlation ID.
⚠️ Nota Crítica O texto afirma "A regra é simples e absoluta: todo consumidor que produz um novo evento copia o correlation ID e define o causation ID como o ID do evento pai." Isso colapsa completamente em cenários fan-in, que são comuns em sistemas EDA reais. Quando um consumidor de saga emite um evento de saída apenas após receber dois ou mais eventos upstream independentes, não há um único evento pai para definir como causation ID. A regra não é absoluta — ela é correta apenas para topologias fan-out.
⚠️ Nota Crítica A dica de "rejeitar qualquer evento interno que chegue sem um correlation ID" quebra eventos produzidos por jobs agendados, pipelines disparados por cron, automação de infraestrutura, capturas CDC de banco de dados. Nenhum desses se origina de uma requisição de borda. A regra qualificada: eventos sintéticos devem gerar seu próprio correlation ID raiz no ponto de emissão.

Lag, Throughput e Métricas de Saúde do Consumidor

Consumer lag é a diferença entre o offset mais recente que um produtor escreveu em uma partição e o offset mais recente que um grupo de consumidores processou. Lag é o equivalente em sistemas distribuídos de uma pilha de tarefas crescente: uma pilha pequena e estável é normal, mas uma pilha que cresce sem limite significa que o consumidor nunca vai se recuperar.

Padrão de lagO que significaAção
Baixo e estávelConsumidor acompanha os produtoresSaudável; nenhuma ação
Dente de serra (sobe, drena)Tráfego em rajadas, consumidor se recuperaNormal; verificar se o pico drena completamente
Subindo constantementeConsumidor é mais lento que o produtorEscalar consumidores horizontalmente ou otimizar o handler
Estável mas alto, sem drenagemConsumidor provavelmente travado ou em crash-loopInvestigar mensagem envenenada imediatamente

💡 Nota do Especialista: O texto distingue corretamente "sobrecarregado" de "travado", mas monitora o throughput agregado do grupo de consumidores, o que oculta um modo de falha crítico: um grupo processando mensagens de dez partições pode mostrar throughput agregado diferente de zero enquanto uma partição está completamente bloqueada por head-of-line. Rastreie lag e throughput no nível por partição, não apenas no nível do grupo de consumidores.
💡 Nota do Especialista A API nativa do Kafka reporta offsets confirmados e offsets de fim de log, mas não expõe carimbos de tempo de mensagens diretamente em forma de lag por idade. O AWS MSK expõe uma métrica do CloudWatch chamada EstimatedMaxTimeLag que fornece o lag baseado em idade diretamente. Para Kafka gerenciado pelo próprio time, o Burrow calcula a saúde do grupo de consumidores usando uma janela deslizante de velocidade de lag em vez de um único snapshot.

Depurando Fluxos de Eventos Assíncronos

Siga um procedimento disciplinado: (1) Ancore no correlation ID. (2) Reconstrua a árvore por causation ID para reconstruir a cadeia causal exata. (3) Encontre a aresta quebrada — o primeiro elo ausente. (4) Inspecione o consumidor suspeito — verifique lag, taxa de erros e a DLQ.

# Log-aggregation incident query: reconstruct the causal chain for one correlation_id
from __future__ import annotations

from dataclasses import dataclass
from typing import Any

INCIDENT_QUERY = """
SELECT
    timestamp,
    event_type,
    service,
    message_id,
    causation_id,
    correlation_id,
    COALESCE(status, 'unknown') AS status
FROM event_log
WHERE correlation_id = :correlation_id
ORDER BY timestamp ASC;
"""


@dataclass
class EventRow:
    timestamp: str
    event_type: str
    service: str
    message_id: str
    causation_id: str
    correlation_id: str
    status: str


def fetch_causal_chain(
    connection,
    correlation_id: str,
) -> list[EventRow]:
    """
    Run the incident query and return rows ordered by timestamp.
    Each row's causation_id points to its parent message_id,
    giving you the exact causal tree without relying on wall-clock order.
    """
    cursor = connection.cursor()
    cursor.execute(
        INCIDENT_QUERY.replace(":correlation_id", "%s"),
        (correlation_id,),
    )
    rows = [EventRow(*row) for row in cursor.fetchall()]
    return rows


def print_causal_tree(rows: list[EventRow]) -> None:
    """
    Pretty-print the chain; highlight any gap where causation_id has no matching message_id.
    The first missing link is almost always where the incident occurred.
    """
    known_ids = {r.message_id for r in rows}
    print(f"{'TIMESTAMP':<30} {'EVENT TYPE':<30} {'SERVICE':<20} {'STATUS':<12} NOTE")
    print("-" * 100)
    for row in rows:
        gap_flag = ""
        if row.causation_id not in known_ids and row.causation_id != row.message_id:
            gap_flag = "  <-- BROKEN LINK (parent not in trace)"
        print(
            f"{row.timestamp:<30} {row.event_type:<30} {row.service:<20} {row.status:<12}{gap_flag}"
        )

Dois avisos conquistados na prática. Primeiro, carimbos de tempo do relógio de parede mentem entre máquinas — confie na cadeia de causalidade. Segundo, resista ao impulso de raciocinar sobre o fluxo a partir do seu diagrama de arquitetura. O diagrama mostra o fluxo que você projetou; o trace de correlação mostra o fluxo que realmente aconteceu. Quando eles discordam, o trace está certo.

💡 Nota do Especialista Em ambientes de nuvem, mesmo com NTP configurado, clock skew entre hosts de 50–200 milissegundos é comum, e em implantações Kubernetes conteinerizadas o skew pode chegar a vários segundos. Armazene o número de sequência atribuído pelo broker ou offset de partição junto ao evento em seu armazenamento de logs e use-o como chave de ordenação autoritativa.

Filas de Mensagens Mortas e Reprocessamento Operacional

Uma DLQ não é uma lata de lixo. É uma fila de trabalho pendente que requer julgamento humano ou automatizado. Cada mensagem nela representa um fato de negócio que não produziu efeito. Portanto: alerte quando a profundidade da DLQ for maior que zero. Uma DLQ não vazia é sempre um incidente, mesmo que pequeno.

Regras de reprocessamento seguro: (1) Corrija a causa antes de reprocessar. (2) Reprocessamento exige idempotência. (3) Preserve os metadados originais — correlation e causation IDs. (4) Reprocesse em lotes controlados.

💡 Nota do Especialista: "Alerte quando a profundidade da DLQ for maior que zero" é correto e importante para equipes no início de sua jornada com EDA, mas em escala produz fadiga de alertas. O refinamento em produção madura é alertar sobre a taxa de crescimento da DLQ (mensagens por minuto) e sobre a idade das mensagens na DLQ excedendo sua janela de SLA de negócio, em vez de profundidade absoluta acima de zero.
⚠️ Nota Crítica: Em sistemas de produção de alto volume, alertar em qualquer mensagem única cria fadiga de alertas crônica, o que leva engenheiros de plantão a começar a suprimir alertas de DLQ — exatamente o oposto do comportamento desejado. Substitua a regra absoluta por uma política graduada: alerte imediatamente sobre a taxa da DLQ (novas mensagens por minuto acima de uma linha de base) e sobre mensagens não reconhecidas além de um SLO baseado em tempo.
💡 Nota do Especialista: Uma dimensão frequentemente esquecida dos metadados originais é a chave de roteamento da mensagem — no Kafka é a chave de partição, no RabbitMQ é a routing key, nas filas FIFO do SQS é o message group ID. Quando operadores drenam uma DLQ usando uma ferramenta de replay genérica, é fácil republicar sem a chave de partição original, fazendo com que a mensagem reprocessada caia em uma partição diferente da original.
⚠️ Nota Crítica A regra "Preserve os metadados originais — reprocesse com os correlation e causation IDs originais" falha silenciosamente ao usar mecanismos nativos de redirecionamento de DLQ do broker. O redirecionamento de dead-letter do AWS SQS e a resubmissão de dead-letter do Azure Service Bus reatribuem um novo MessageId em nível de broker à mensagem reenfileirada. Sempre incorpore correlation e causation IDs no corpo da mensagem ou em headers definidos pela aplicação (não em campos nativos do broker).

Mensagens Envenenadas e Estratégias de Contenção

A mensagem envenenada (poison message) é um evento cujo conteúdo desencadeia uma falha determinística no consumidor todas as vezes. Em uma partição ordenada, uma mensagem envenenada causa bloqueio head-of-line: porque o consumidor deve processar mensagens em ordem e não consegue passar por esta, cada mensagem atrás dela também está presa.

A contenção repousa em três mecanismos: (1) Tentativas limitadas com backoff — após um pequeno número de tentativas, desista e roteie para a DLQ. (2) Rotear para a DLQ para desbloquear a partição. (3) Validar na borda — a validação de schema na ingestão captura a maioria dos payloads malformados.

# Bounded-retry consumer loop with DLQ routing to prevent head-of-line blocking
from __future__ import annotations

import logging
import time
from dataclasses import dataclass
from typing import Callable

logger = logging.getLogger(__name__)

MAX_ATTEMPTS = 3
BASE_BACKOFF_SECONDS = 1


@dataclass
class MessageContext:
    """Thin wrapper around a broker message carrying the envelope and ack handle."""
    envelope: "EventEnvelope"
    raw_payload: bytes
    ack: Callable[[], None]
    nack: Callable[[], None]


def process_with_dlq_fallback(
    ctx: MessageContext,
    handler: Callable[["EventEnvelope"], None],
    dlq_publisher,
    dlq_topic: str,
) -> None:
    """
    Attempt to process a message up to MAX_ATTEMPTS times with exponential backoff.
    On final failure, publish to the DLQ with diagnostic metadata and acknowledge
    the original so the partition advances past the poison message.
    """
    last_exception: Exception | None = None

    for attempt in range(1, MAX_ATTEMPTS + 1):
        try:
            handler(ctx.envelope)
            ctx.ack()
            return

        except Exception as exc:
            last_exception = exc
            logger.warning(
                "Handler failed (attempt %d/%d) for message_id=%s: %s",
                attempt,
                MAX_ATTEMPTS,
                ctx.envelope.message_id,
                exc,
            )
            if attempt < MAX_ATTEMPTS:
                backoff = BASE_BACKOFF_SECONDS * (2 ** (attempt - 1))
                time.sleep(backoff)

    dead_letter_payload = {
        "original_message_id": ctx.envelope.message_id,
        "original_event_type": ctx.envelope.event_type,
        "original_payload": ctx.envelope.payload,
        "correlation_id": ctx.envelope.correlation_id,
        "causation_id": ctx.envelope.causation_id,
        "dead_letter_reason": str(last_exception),
        "retry_count": MAX_ATTEMPTS,
    }

    try:
        dlq_publisher.publish(topic=dlq_topic, payload=dead_letter_payload)
        logger.error(
            "Poison message routed to DLQ after %d attempts: message_id=%s reason=%s",
            MAX_ATTEMPTS,
            ctx.envelope.message_id,
            last_exception,
        )
    except Exception as dlq_exc:
        logger.critical(
            "CRITICAL: DLQ publish failed for message_id=%s. Acknowledging anyway to unblock "
            "partition. Manual recovery required. dlq_error=%s original_error=%s",
            ctx.envelope.message_id,
            dlq_exc,
            last_exception,
        )

    ctx.ack()
💡 Nota do Especialista A validação de schema na fronteira do broker captura violações de contrato estrutural, mas não captura mensagens envenenadas semânticas — eventos que são estruturalmente válidos contra o schema, mas contêm valores que desencadeiam falhas determinísticas em consumidores específicos: um ID de produto que existe no schema como uma string não nula, mas se refere a um registro deletado; um valor numérico zero que causa uma divisão por zero.
⚠️ Nota Crítica O texto afirma "Schema validation at ingestion catches most malformed payloads." Isso superestima significativamente a cobertura da validação de schema. Os registries de schema validam conformidade estrutural (tipos de campo, campos obrigatórios). Eles não capturam as mensagens envenenadas mais comuns do mundo real: um inteiro sintaticamente válido que causa divisão por zero; um valor nulo em um campo opcional que o consumidor desreferencia sem uma guarda.

Principais Conclusões

  • Correlation IDs agrupam uma transação de negócio inteira; causation IDs reconstroem a cadeia causal exata pai-filho. Todo consumidor produtor deve copiar o correlation ID e definir o causation ID como o message ID de seu pai.
  • Consumer lag é seu principal sinal de saúde. Alerte sobre sua tendência e sobre a idade da mensagem não processada mais antiga, e combine-o com throughput para distinguir "sobrecarregado" de "travado".
  • Depure retroativamente a partir do correlation ID, não do diagrama de arquitetura. Confie na cadeia de causalidade em vez dos carimbos de tempo do relógio de parede.
  • Uma DLQ não vazia é sempre um incidente. Corrija a causa raiz primeiro, dependa de idempotência, preserve os metadados originais e reprocesse em lotes com limitação de velocidade.
  • Mensagens envenenadas causam bloqueio head-of-line. Contenha-as com tentativas limitadas, roteamento para DLQ para desbloquear a partição, e validação de borda.
