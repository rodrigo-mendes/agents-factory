Capítulo 7: Consistência, Sagas e Processos de Longa Duração

Problema de Abertura

O Capítulo 6 deixou o lado de escrita resolvido: o estado é um log imutável de eventos, e a verdade reside no event store. Mas aquele capítulo assumiu silenciosamente uma fronteira confortável — um agregado, um stream, uma transação. Os processos de negócio reais não são tão educados. Realizar um pedido envolve estoque, pagamento e entrega. Cada um desses elementos vive em um serviço diferente, atrás de um banco de dados diferente, pertencente a uma equipe diferente.

Aqui está a questão desconfortável que este capítulo responde: como você mantém três serviços consistentes quando não pode envolvê-los em uma única transação? O instinto clássico — uma transação distribuída que bloqueia os três e confirma atomicamente — soa correto e está quase sempre errado em um sistema cloud-native. A alternativa é a saga: uma sequência de transações locais, cada uma confirmando independentemente, coordenadas por eventos, e revertidas não por rollback, mas por compensação.

Consistência Eventual Versus Consistência Forte

Consistência forte significa que, uma vez concluída uma escrita, toda leitura subsequente — de qualquer lugar — verá essa escrita. Consistência eventual faz uma promessa mais fraca: se as escritas pararem, todas as réplicas e visões derivadas eventualmente convergirão para o mesmo valor. Entre a escrita e essa convergência, existe uma janela na qual diferentes partes do sistema discordam. Essa janela não é um bug. É o preço de manter os serviços independentes e disponíveis.

💡 Nota do Especialista O texto apresenta a consistência como binária (forte vs. eventual), o que é pedagogicamente útil, mas pode levar arquitetos a projetar em excesso. Na prática, muitos requisitos de UX e API precisam apenas de consistência "read-your-writes" (causal) — o usuário que acabou de criar um recurso pode vê-lo na próxima requisição, mas outros usuários verem uma visão ligeiramente desatualizada é aceitável. Projetar para read-your-writes frequentemente elimina a necessidade de chamadas síncronas entre serviços.

Por Que Transações ACID Distribuídas Falham

O two-phase commit (2PC) tem três propriedades fatais para sistemas cloud-native. Primeiro, ele mantém bloqueios pela rede — entre prepare e commit, cada participante mantém suas linhas bloqueadas. Segundo, é um protocolo bloqueante — se o coordenador falhar após os participantes votarem sim, os participantes ficam presos no estado "in-doubt". Terceiro, ele acopla disponibilidade — uma transação só tem sucesso se todos os participantes estiverem ativos ao mesmo tempo.

# O(n) per phase where n = number of participants; locks held across both phases are the core hazard
from __future__ import annotations

import enum
from dataclasses import dataclass


class VoteResult(enum.Enum):
    YES = "yes"
    NO = "no"


class CoordinatorState(enum.Enum):
    IDLE = "IDLE"
    PREPARING = "PREPARING"
    COMMITTED = "COMMITTED"
    ABORTED = "ABORTED"
    IN_DOUBT = "IN_DOUBT"


@dataclass
class Participant:
    """Represents one service participating in the distributed transaction."""
    name: str
    vote: VoteResult = VoteResult.YES
    locked: bool = False
    committed: bool = False

    def prepare(self) -> VoteResult:
        self.locked = True
        return self.vote

    def commit(self) -> None:
        self.locked = False
        self.committed = True

    def abort(self) -> None:
        self.locked = False
        self.committed = False


class TwoPhaseCommitCoordinator:
    """Drives the two phases; exposes the crash-induced in-doubt scenario."""

    def __init__(self, participants: list[Participant]) -> None:
        self.participants = participants
        self.state = CoordinatorState.IDLE
        self._votes: dict[str, VoteResult] = {}

    def run(self, simulate_crash_after_prepare: bool = False) -> CoordinatorState:
        self.state = CoordinatorState.PREPARING
        for p in self.participants:
            vote = p.prepare()
            self._votes[p.name] = vote
            print(f"  {p.name:20s}  voted {vote.value:3s}  locked={p.locked}")

        all_yes = all(v == VoteResult.YES for v in self._votes.values())

        if simulate_crash_after_prepare:
            self.state = CoordinatorState.IN_DOUBT
            stuck = [p.name for p in self.participants if p.locked]
            print(f"\n  *** COORDINATOR CRASHED — in-doubt participants (locks held): {stuck} ***")
            return self.state

        if all_yes:
            for p in self.participants:
                p.commit()
            self.state = CoordinatorState.COMMITTED
        else:
            for p in self.participants:
                p.abort()
            self.state = CoordinatorState.ABORTED

        return self.state
💡 Nota do Especialista: O texto identifica corretamente o 2PC como o padrão a ser substituído, mas perde uma armadilha corporativa: transações XA (@Transactional do Spring abrangendo múltiplos beans DataSource, MSDTC no .NET) são 2PC disfarçados. Audite seu grafo de dependências antes de declarar que eliminou o 2PC de um caminho de migração legado.
⚠️ Nota Crítica O capítulo enquadra o 2PC como uma escolha puramente "CP". Isso é uma simplificação excessiva que o próprio estado in-doubt já refuta: quando o coordenador falha após os participantes terem votado sim, mas antes de a decisão de commit ser transmitida, o sistema não é nem disponível nem consistente — está travado. A caracterização do 2PC como CP é uma abreviação útil para o trade-off de tolerância a partições, mas a garantia "C" se degrada sob falha do coordenador.

Sagas Coreografadas Versus Orquestradas

Em uma saga coreografada, não há coordenador central. Cada serviço escuta eventos, realiza seu trabalho local e emite seu próprio evento. Em uma saga orquestrada, um coordenador dedicado — o orquestrador — é dono do processo. Ele envia comandos explícitos, aguarda respostas e decide a próxima etapa.

💡 Nota do Especialista: O Outbox Pattern não é opcional para sagas coreografadas em produção. Se um serviço confirma sua transação local, mas falha antes de publicar o evento downstream, a saga estagna silenciosamente. Gravar o evento em uma tabela outbox local na mesma transação ACID é o mecanismo que torna a coreografia confiável.
💡 Nota do Especialista A estratégia de testes diverge acentuadamente entre as duas topologias. Sagas coreografadas requerem contract testing entre fronteiras de serviços (Pact, Spring Cloud Contract) para verificar que um evento publicado pelo Serviço A satisfaz o schema do consumidor do Serviço B. Sagas orquestradas podem ser testadas unitariamente em isolamento: simule os canais de comando downstream, alimente eventos de resposta, asserte transições de estado.

Transações Compensatórias e Rollback Semântico

O coração da saga é o que acontece quando a quarta etapa falha após as etapas um a três terem sido concluídas. Não há ROLLBACK — essas transações já foram confirmadas. Em vez disso, a saga executa transações compensatórias: novas transações que semanticamente desfazem o efeito das concluídas. Você não descobre um cartão de crédito — você emite um reembolso.

# Saga execution — O(n) forward, O(k) compensation where k = steps completed before failure
from __future__ import annotations

import enum
from dataclasses import dataclass, field
from typing import Callable


class StepStatus(enum.Enum):
    PENDING = "pending"
    COMPLETED = "completed"
    COMPENSATED = "compensated"
    FAILED = "failed"


@dataclass
class SagaStep:
    """Pairs a forward business action with its semantic compensation."""
    name: str
    action: Callable[[], None]
    compensation: Callable[[], None]
    status: StepStatus = field(default=StepStatus.PENDING, init=False)


class OrderSaga:
    """
    Executes an order saga: ReserveStock -> CapturePayment -> CreateShipment.
    On any failure, compensates completed steps in reverse order.
    """

    def __init__(self, order_id: str) -> None:
        self.order_id = order_id
        self.steps: list[SagaStep] = [
            SagaStep("ReserveStock",   self._reserve_stock,   self._release_stock),
            SagaStep("CapturePayment", self._capture_payment, self._refund_payment),
            SagaStep("CreateShipment", self._create_shipment, self._cancel_shipment),
        ]

    def _reserve_stock(self) -> None:
        print(f"  [ReserveStock]   stock reserved   order={self.order_id}")

    def _capture_payment(self) -> None:
        print(f"  [CapturePayment] charging card     order={self.order_id}")
        raise RuntimeError("Payment gateway timeout — no charge was made")

    def _create_shipment(self) -> None:
        print(f"  [CreateShipment] shipment created  order={self.order_id}")

    def _release_stock(self) -> None:
        print(f"  [ReleaseStock]   stock released    order={self.order_id}")

    def _refund_payment(self) -> None:
        print(f"  [RefundPayment]  refund issued     order={self.order_id}")

    def _cancel_shipment(self) -> None:
        print(f"  [CancelShipment] shipment cancelled order={self.order_id}")

    def execute(self) -> bool:
        """
        Run forward steps in order. On the first failure, compensate every
        previously completed step in reverse order (LIFO), then return False.
        """
        completed: list[SagaStep] = []

        for step in self.steps:
            try:
                step.action()
                step.status = StepStatus.COMPLETED
                completed.append(step)
            except Exception as exc:
                step.status = StepStatus.FAILED
                print(f"\n  Step '{step.name}' failed: {exc}")
                print("  Compensating completed steps in reverse order...")
                for done in reversed(completed):
                    done.compensation()
                    done.status = StepStatus.COMPENSATED
                return False

        return True

Três propriedades tornam as compensações confiáveis: (1) devem ser idempotentes — use uma chave de compensação e verifique "já foi compensado?" antes de agir; (2) devem ser executadas em ordem inversa às etapas avançadas; (3) algumas ações não podem ser compensadas — essas são transações pivot que devem vir por último, após todas as etapas compensáveis.

💡 Nota do Especialista: O texto estabelece que as compensações devem ser idempotentes, mas não aborda o caso em que a própria compensação falha. Quando a transação compensatória não pode ser entregue ou é rejeitada, a saga fica presa em um estado parcialmente compensado. Sistemas de produção devem modelar um estado terminal CompensationFailed respaldado por uma dead-letter queue, uma regra de alertas e um playbook de remediação manual.
⚠️ Nota Crítica: A seção inteira sobre compensações descreve uma única instância de saga em isolamento e nunca aborda o problema de isolamento da saga: porque cada transação local confirma independentemente e os estados intermediários da saga são totalmente visíveis, as sagas sofrem de leituras sujas e atualizações perdidas. Um processo concorrente lendo o registro de pedido entre PaymentCaptured e ShipmentCreated vê um estado que pode ser compensado posteriormente.
⚠️ Nota Crítica A Propriedade 2 afirma "Compensações devem ser seguras com relação à comutatividade de ordenação" — isso é um erro de terminologia. Comutatividade significa que a ordem das operações não importa. O texto então instrui o leitor a executar compensações em ordem inversa, que é o oposto de um requisito de comutatividade. O que a propriedade realmente requer é uma ordenação sequencial inversa estrita.

Gerenciadores de Processo e Máquinas de Estado

Um orquestrador real deve lembrar: quais etapas foram concluídas, quais estão pendentes, o que fazer em cada resposta, quando atingir o timeout e quando começar a compensar. Esse coordenador com estado é o gerenciador de processo (process manager), e sua implementação mais confiável é uma máquina de estado explícita.

Duas disciplinas separam um gerenciador de processo robusto de um frágil. Primeiro, persista o estado da saga em cada transição — um gerenciador de processo que mantém o estado apenas em memória irá abandonar todos os pedidos em voo no primeiro reinício do pod. Segundo, trate timeouts como estados de primeira classe — uma etapa que nunca responde simplesmente aguarda para sempre; o gerenciador deve definir um timer em cada etapa pendente e disparar compensação ao expirar.

💡 Nota do Especialista O texto recomenda Temporal, AWS Step Functions e Camunda como escolhas razoáveis. No entanto, seus modelos de durabilidade diferem: o Temporal reconstrói o estado do workflow repetindo um histórico de eventos; o AWS Step Functions impõe limites rígidos (25.000 eventos de histórico por execução) que afetam processos de longa duração; o Camunda 8 usa o log replicado do Zeebe. Avalie o modelo de durabilidade e o footprint operacional antes de se comprometer.
💡 Nota do Especialista Um anti-padrão comum é codificar regras de negócio dentro do próprio orquestrador — ramificações condicionais baseadas em tier do cliente, lógica de precificação, verificações de conformidade. O orquestrador deve emitir comandos e receber respostas; deve conter apenas fluxo de controle. Quando o orquestrador cresce além de algumas centenas de linhas de lógica de controle, torna-se tão difícil de mudar quanto o monólito que a saga substituiu.

Teorema CAP Aplicado a Fluxos de Eventos

O teorema CAP afirma que um sistema distribuído, quando uma partição (P) de rede o divide, pode preservar ou consistência (C) — todos os nós veem os mesmos dados — ou disponibilidade (A) — toda requisição recebe uma resposta — mas não ambas. Transações distribuídas e 2PC são a escolha CP. Sagas são a escolha AP: sob uma partição, cada transação local ainda confirma, o sistema permanece disponível e a consistência é restaurada depois.

📊 [Diagram — Mermaid source below]

flowchart TD
    A[Cross-Service Business Operation] --> B{Network Partition Detected?}
    B -->|No| N[Proceed Normally]
    B -->|Yes| D{CAP Choice}
    D -->|Choose Consistency - CP| E[Block — Wait for All Participants]
    E --> F[2PC Coordinator Holds Locks]
    F --> G[Operation Fails\nData remains consistent\nBusiness request rejected]
    D -->|Choose Availability - AP| H[Commit Locally per Service]
    H --> I[Each Service Stays Available\nSaga Continues]
    I --> J[Eventual Convergence\nvia Events and Compensations\nBusiness request accepted]

O CAP não é uma propriedade do seu sistema inteiro; é uma propriedade de cada operação. Arquiteturas maduras são fortemente consistentes dentro de cada fronteira de serviço e eventualmente consistentes entre fronteiras, com as sagas como a ponte entre os dois regimes.

⚠️ Nota Crítica O teorema CAP é apresentado como um framework completo e atual, mas suas limitações práticas são bem estabelecidas. O próprio Eric Brewer reconheceu em sua retrospectiva de 2012 que o enquadramento binário obscurece mais do que revela. O teorema PACELC (Abadi, 2012) — que estende o CAP para abordar o trade-off latência/consistência que existe mesmo quando não há partição — é o modelo operacionalmente mais relevante para arquitetos projetando sistemas orientados a eventos.

Principais Conclusões

  • Transações ACID distribuídas não escalam. O two-phase commit mantém bloqueios pela rede, bloqueia sob falha do coordenador e multiplica a fragilidade. Rejeite-o para processos de negócio entre serviços.
  • Uma saga é uma sequência de transações locais coordenadas por eventos, revertida por compensação, não por rollback. Ela aceita consistência eventual para preservar disponibilidade e independência dos serviços.
  • Coreografe fluxos curtos e estáveis; orquestre os complexos ou com ramificações. Além de três ou quatro etapas, prefira a orquestração.
  • Compensações são novas ações de negócio, não desfazimentos técnicos. Classifique cada etapa como compensável, pivot ou retriable, e ordene a saga para que a irreversibilidade venha por último.
  • Um gerenciador de processo é uma máquina de estado persistente. Persista o estado em cada transição e trate timeouts como eventos de primeira classe.
  • Sagas são a escolha AP do teorema CAP. Consistência forte dentro de cada fronteira de serviço, consistência eventual entre fronteiras.

O Que Vem a Seguir

As sagas dependem de eventos cujo significado permanece estável entre serviços e ao longo do tempo — o que levanta o problema que o Capítulo 8 enfrenta diretamente: como evoluir schemas e contratos de eventos sem quebrar os consumidores.
