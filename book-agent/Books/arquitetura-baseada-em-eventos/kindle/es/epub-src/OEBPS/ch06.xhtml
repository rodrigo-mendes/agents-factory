Capítulo 6: Event Sourcing — El Estado como una Secuencia de Eventos

Planteamiento del Problema Inicial

El Capítulo 5 mostró que los modelos de lectura son descartables — puedes eliminarlos y reconstruirlos reproduciendo eventos. Esa afirmación asumía en silencio algo que nunca justificamos: que los eventos siguen existiendo en algún lugar, en orden, para siempre. Event Sourcing (almacenamiento de eventos) es el patrón en el que el estado autoritativo de una entidad no es una fila que se actualiza, sino la secuencia completa y ordenada de eventos que le ocurrieron.

El Problema de la Verdad y la Historia

Los sistemas tradicionales tienen un problema de memoria: olvidan. Cuando un cliente retira dinero, ejecutas un UPDATE y el saldo anterior desaparece. La base de datos ahora contiene un hecho — "el saldo es 500" — pero ha destruido la historia que lo produjo. Este es el problema de la verdad y la historia.

En un sistema basado en Event Sourcing, la historia es el modelo de almacenamiento. No puedes tener una historia incorrecta, porque la historia es lo único que alguna vez escribiste. La corrección del registro de auditoría deja de ser una característica que se mantiene y se convierte en una propiedad de la arquitectura.

⚠️ Nota Crítica: El texto afirma "no puedes tener una historia incorrecta, porque la historia es lo único que alguna vez escribiste." Esto es una exageración significativa. Los errores en la capa de aplicación — emitir un evento MoneyWithdrawn con el monto incorrecto o disparar dos veces un manejador de comandos — producen eventos incorrectos que se persisten de forma permanente con la misma garantía de inmutabilidad que los eventos correctos. El almacén de eventos garantiza solo adición y ordenamiento, no la corrección del dominio.
💡 Nota del Experto

Los triggers de auditoría omiten los estados intermedios dentro de las transacciones de múltiples declaraciones. Más insidiosamente, cuando cambia el esquema (se renombra o elimina una columna), la definición del trigger se rompe silenciosamente o comienza a registrar null para ese campo, sin que se genere ningún error. Event Sourcing evita esto por completo porque la intención — el evento de negocio — es lo que se escribe, no la mutación de la fila.

El Almacén de Eventos y el Registro de Solo Adición

La base de datos que contiene estos eventos se denomina almacén de eventos (event store). Es un registro especializado con dos reglas que definen todo el patrón. Primero, el almacén de eventos es de solo adición (append-only). Segundo, los eventos se agrupan en flujos (streams) — la secuencia ordenada de todos los eventos de una entidad.

# Python 3.10+ -- event store schema setup using psycopg2
# global_position provides monotone total order across all streams;
# UNIQUE (stream_id, version) enforces per-stream ordering and acts as the
# optimistic concurrency guard.

import psycopg2

_CREATE_TABLE = """
CREATE TABLE IF NOT EXISTS event_store (
    global_position  BIGSERIAL    PRIMARY KEY,
    stream_id        TEXT         NOT NULL,
    version          INTEGER      NOT NULL,
    event_type       TEXT         NOT NULL,
    payload          JSONB        NOT NULL,
    metadata         JSONB        NOT NULL DEFAULT '{}',
    occurred_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT uq_stream_version UNIQUE (stream_id, version)
);
"""


def setup_event_store(conn) -> None:
    """Create the event_store table and supporting indexes if they do not exist."""
    with conn:
        with conn.cursor() as cur:
            cur.execute(_CREATE_TABLE)

La columna version garantiza un orden total dentro de cada flujo y proporciona control de concurrencia optimista. Cuando un manejador de comandos carga un flujo, anota la versión más alta actual — digamos, 7. Procesa el comando e intenta añadir un nuevo evento como versión 8. Si otro proceso ya escribió la versión 8 mientras tanto, la restricción única rechaza la inserción.

# Python 3.10+ -- optimistic concurrency append using psycopg2
from __future__ import annotations

import json
from dataclasses import dataclass, field
from typing import Any

import psycopg2
from psycopg2 import errors as pg_errors


@dataclass
class EventRecord:
    stream_id:  str
    event_type: str
    payload:    dict[str, Any]
    metadata:   dict[str, Any] = field(default_factory=dict)


class ConcurrencyConflictError(Exception):
    """Raised when another writer already appended at the expected version."""


def append_events(conn, stream_id: str, events: list[EventRecord], expected_version: int) -> None:
    with conn:
        with conn.cursor() as cur:
            for offset, event in enumerate(events):
                next_version = expected_version + 1 + offset
                try:
                    cur.execute(
                        """
                        INSERT INTO event_store
                            (stream_id, version, event_type, payload, metadata)
                        VALUES (%s, %s, %s, %s::jsonb, %s::jsonb)
                        """,
                        (stream_id, next_version, event.event_type,
                         json.dumps(event.payload), json.dumps(event.metadata)),
                    )
                except pg_errors.UniqueViolation:
                    raise ConcurrencyConflictError(
                        f"Concurrency conflict on stream '{stream_id}': "
                        f"expected version {expected_version} is stale. Reload and retry."
                    )
💡 Nota del Experto: La columna global_position en el esquema es fácil de implementar incorrectamente en PostgreSQL con un BIGSERIAL. Las secuencias de PostgreSQL son no transaccionales por diseño: si una transacción inserta un evento y luego hace rollback, el valor de la secuencia se consume y no se reutiliza. Los consumidores que leen global_position en orden verán brechas y deben decidir si una brecha significa "aún no confirmado" o "permanentemente faltante."
💡 Nota del Experto

Al comparar EventStoreDB con un almacén PostgreSQL hecho en casa, el diferenciador práctico corporativo es la semántica de suscripción, no el almacenamiento. Las suscripciones persistentes de EventStoreDB admiten un modelo de consumidores en competencia por grupo de forma nativa, pero su motor de proyecciones introduce una carga operacional que la mayoría de los equipos empresariales subestiman.

⚠️ Nota Crítica

La afirmación "sin bloqueos, sin espera — solo una restricción haciendo su trabajo" sobreestima el beneficio de la concurrencia optimista bajo contensión. En escenarios de escritura de alto rendimiento en un único flujo de agregado, cada escritor en conflicto reintentará. Bajo contensión sostenida, esto degrada a una serialización efectiva. La concurrencia optimista funciona mejor cuando los escritores en conflicto en el mismo flujo son raros.

Reconstrucción de Estado y Agregados

Si nunca almacenas el estado actual, ¿cómo lo obtienes? Lo calculas. El proceso se denomina reconstrucción o rehidratación: lees el flujo desde el principio y aplicas cada evento, en orden, a un objeto en memoria nuevo. Ese objeto es el agregado (aggregate).

# Python 3.10+ -- Account aggregate with strict command / apply separation
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Union


@dataclass(frozen=True)
class AccountOpened:
    account_id: str
    owner:      str

@dataclass(frozen=True)
class MoneyDeposited:
    account_id: str
    amount:     int

@dataclass(frozen=True)
class MoneyWithdrawn:
    account_id: str
    amount:     int

DomainEvent = Union[AccountOpened, MoneyDeposited, MoneyWithdrawn]


@dataclass
class Account:
    account_id: str  = ""
    owner:      str  = ""
    balance:    int  = 0
    version:    int  = 0
    _pending:   list[DomainEvent] = field(default_factory=list, repr=False)

    @classmethod
    def open(cls, account_id: str, owner: str) -> "Account":
        aggregate = cls()
        aggregate._record(AccountOpened(account_id=account_id, owner=owner))
        return aggregate

    def deposit(self, amount: int) -> None:
        if amount <= 0:
            raise ValueError(f"Deposit amount must be positive, got {amount}.")
        self._record(MoneyDeposited(account_id=self.account_id, amount=amount))

    def withdraw(self, amount: int) -> None:
        if amount <= 0:
            raise ValueError(f"Withdrawal amount must be positive, got {amount}.")
        if amount > self.balance:
            raise ValueError(f"Insufficient funds: balance={self.balance}, requested={amount}.")
        self._record(MoneyWithdrawn(account_id=self.account_id, amount=amount))

    def _apply(self, event: DomainEvent) -> None:
        """Mutate in-memory state. Must never raise."""
        match event:
            case AccountOpened(account_id=aid, owner=owner):
                self.account_id = aid
                self.owner      = owner
                self.balance    = 0
            case MoneyDeposited(amount=amount):
                self.balance += amount
            case MoneyWithdrawn(amount=amount):
                self.balance -= amount

    def _record(self, event: DomainEvent) -> None:
        self._apply(event)
        self._pending.append(event)

    @classmethod
    def rehydrate(cls, events: list[DomainEvent]) -> "Account":
        aggregate = cls()
        for i, event in enumerate(events, start=1):
            aggregate._apply(event)
            aggregate.version = i
        return aggregate

Hay exactamente dos tipos de métodos en el agregado:

  1. Los métodos de comando (por ejemplo, withdraw) contienen las reglas de negocio. Validan invariantes y, si la regla se cumple, producen un nuevo evento.
  2. Los métodos de aplicación (por ejemplo, _apply) no contienen ninguna lógica de negocio. Solo mutan el estado en memoria a partir de un evento que ya ocurrió.

La regla es absoluta: los métodos de aplicación nunca deben rechazar un evento ni contener validación.

💡 Nota del Experto

El patrón de implementación estándar añade un detalle estructural: el agregado mantiene una lista interna de "eventos no confirmados." Cuando un método de comando decide aceptar una acción de negocio, llama a su propio apply() internamente — para actualizar el estado en memoria de inmediato — y añade el evento a esta lista. El repositorio, después de llamar al comando, lee la lista de no confirmados y añade esos eventos al almacén en la versión esperada.

⚠️ Nota Crítica

La regla "los métodos de aplicación nunca deben rechazar un evento ni contener validación" se describe como absoluta, pero no aborda el escenario de compatibilidad hacia adelante en el que un agregado encuentra un tipo de evento introducido por una versión más reciente de la aplicación que el código actual no reconoce. Para tipos de eventos desconocidos, la estrategia recomendada es ignorar-y-registrar con una verificación de conciencia de versión.

Snapshots y Optimización de Reproducción

Si una cuenta ha acumulado 200.000 eventos a lo largo de diez años, ¿debes leer y plegar los 200.000 eventos cada vez que alguien consulta el saldo? La respuesta es el snapshot (instantánea): una copia en caché del estado del agregado en una versión específica. La reconstrucción cambia entonces: carga el snapshot más reciente y reproduce solo los eventos que vinieron después de él.

# Python 3.10+ -- snapshot-based rehydration with full-replay fallback
from __future__ import annotations

from dataclasses import dataclass
from typing import Any, Optional


@dataclass
class Snapshot:
    stream_id: str
    version:   int
    state:     dict[str, Any]


def rehydrate_from_snapshot(stream_id: str) -> Account:
    """Reconstruct an Account aggregate, using a snapshot when available."""
    snapshot: Optional[Snapshot] = load_latest_snapshot(stream_id)

    if snapshot is not None:
        aggregate = Account(
            account_id=snapshot.state["account_id"],
            owner=snapshot.state["owner"],
            balance=snapshot.state["balance"],
        )
        aggregate.version = snapshot.version
        delta_events = load_events_after_version(stream_id, after_version=snapshot.version)
    else:
        aggregate = Account()
        delta_events = load_events_after_version(stream_id, after_version=0)

    for event in delta_events:
        aggregate._apply(event)
        aggregate.version += 1

    return aggregate


def maybe_take_snapshot(aggregate: Account, interval: int = 100) -> Optional[Snapshot]:
    if aggregate.version > 0 and aggregate.version % interval == 0:
        return Snapshot(
            stream_id=aggregate.account_id,
            version=aggregate.version,
            state={"account_id": aggregate.account_id, "owner": aggregate.owner, "balance": aggregate.balance},
        )
    return None

Dos puntos de diseño clave:

  • Un snapshot es una optimización derivada, nunca una fuente de verdad. Debes poder eliminar todos los snapshots y reconstruirlos a partir de los eventos.
  • Toma snapshots en una cadencia, no en cada escritura. Una política común es un snapshot cada N eventos por flujo — digamos, cada 100.

💡 Nota del Experto: Un error en cualquier método apply() que pase desapercibido durante semanas corromperá silenciosamente cada snapshot generado durante ese período. La solución en producción es adjuntar un snapshot_schema_version a cada fila de snapshot. Al cargar, si snapshot_schema_version no coincide con la versión del código actual, descarta el snapshot y cae de nuevo a la reproducción completa.
💡 Nota del Experto

El texto enmarca los snapshots como un parámetro de ajuste en la lectura, pero importa igualmente en la ruta de escritura. Los sistemas en producción casi universalmente hacen los snapshots asíncronos: un trabajador en segundo plano detecta que un flujo ha avanzado más allá de un umbral y escribe el snapshot fuera de banda. La ruta de comandos se mantiene rápida y predecible.

⚠️ Nota Crítica

La discusión sobre la estrategia de snapshots omite una pregunta operacional crítica: ¿quién escribe el snapshot y qué ocurre si esa escritura falla? Los snapshots deben escribirse como operaciones de mejor esfuerzo, no transaccionales, que nunca bloqueen ni hagan fallar el pipeline de comandos.

Costos a Largo Plazo y Restricciones de Diseño

Event Sourcing no es una técnica que pruebas durante un sprint y abandonas limpiamente. Sus costos son permanentes:

  • Los eventos son permanentes, por lo tanto sus esquemas son permanentes. No puedes migrar el pasado. Acomodas las formas antiguas mediante versionado y upcasting — todo el tema del Capítulo 8.
  • La eliminación se convierte en un problema de diseño real. El GDPR otorga el derecho al olvido, lo que choca frontalmente con un registro inmutable. La respuesta estándar es el crypto-shredding: cifrar los datos personales por sujeto y eliminar la clave para hacer los datos irrecuperables.
  • Consultar el estado actual requiere el lado de lectura. Dado que el estado es derivado, necesitas proyecciones y modelos de lectura. Elegir Event Sourcing te compromete efectivamente con la ruta de lectura CQRS del Capítulo 5.

Event Sourcing justifica su costo en dominios donde la historia es intrínsecamente valiosa — libros contables, operaciones bursátiles, seguros, ciclos de vida de pedidos — y donde el negocio genuinamente pregunta cómo llegamos aquí.

💡 Nota del Experto: El crypto-shredding tal como se describe es correcto, pero subestima una restricción de implementación crítica: los datos personales no pueden aparecer en ningún lugar fuera del payload cifrado — no en el nombre del tipo de evento, no en los campos de metadatos, y no en los IDs de flujo que codifican un nombre de usuario o correo electrónico. La disciplina arquitectónica es usar identificadores opacos (UUIDs) como IDs de flujo desde el primer día.
⚠️ Nota Crítica

El texto cita los registros médicos como un dominio canónico donde Event Sourcing "justifica su costo." Este es el mismo dominio donde HIPAA y GDPR crean una obligación de derecho al olvido y donde la corrección de datos (enmendar una entrada clínica) es un requisito operacional rutinario. La inmutabilidad de Event Sourcing está en tensión directa con ambos. Los libros contables financieros y el ciclo de vida de pedidos son ejemplos canónicos más limpios.

Conclusiones Clave

  • Event Sourcing almacena cada evento que cambia el estado como un hecho inmutable y deriva el estado actual mediante reproducción, resolviendo el problema de la verdad y la historia que crean los sistemas de actualización en el lugar al olvidar el pasado.
  • El almacén de eventos (event store) es de solo adición y está organizado en flujos por entidad; una restricción UNIQUE (stream_id, version) garantiza tanto el ordenamiento como la concurrencia optimista sin bloqueos.
  • Los agregados son rehidratados al plegar los eventos en orden; los métodos de comando validan invariantes y emiten eventos, mientras que los métodos de aplicación solo mutan el estado.
  • Los snapshots acotan el costo de reproducción al crear puntos de control del estado cada N eventos, pero son optimizaciones descartables — nunca una fuente de verdad.
  • Los costos son esquemas permanentes, eliminación difícil (crypto-shredding) y un lado de lectura obligatorio; adopta Event Sourcing solo donde la historia sea genuinamente valiosa para el negocio.
