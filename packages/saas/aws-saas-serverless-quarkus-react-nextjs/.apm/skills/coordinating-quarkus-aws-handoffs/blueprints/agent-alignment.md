# Agent alignment

Back to [SKILL.md](../SKILL.md). What each agent emits against what `assets/handoff-profile.yaml` expects, the mismatches found
(ids **A1-A16**, unique in this skill; the register of unverified items uses U/M ids), and how the profile or the orchestrator
absorbs each. Rows for the new agents (A14-A16) describe the **contract this profile requires of them**; their agent definitions now exist (re-check each row against its agent file when either changes); they are
authored separately, so re-read each agent file against its row before first use (the 2026-10-28 reading covers only the agents that already existed).
Rules 14-15 of the family decide the vocabulary: agents use the protocol's outcomes (report family `success|partial|failed|needs-input`,
verify `pass|fail`) and the profile carries no `values:` override. Agents are not edited by this skill; list any needed agent change in the hand-back.

## Routing details the profile expresses

- Event rules are first-match, after `limit_reached`, `drift: true` (-> `sync`) and
  `pending_deltas > 0` (-> `orchestrator`): a drift or an open delta is never shadowed by a later
  event rule (an author `success` with an open divergence goes to `sync` before the reviewer).
- Design: `success` of `solution-architect` -> `solution-reviewer`, of `infrastructure-architect` -> `infrastructure-reviewer`,
  of `designer` -> `design-reviewer`; `needs-input` of any of the three -> `orchestrator` (the user is asked). A `verify` `fail` of
  any reviewer -> `orchestrator`; a `pass` matches no rule and falls to the fallback (`orchestrator`), which shows the user or starts the next front.
- Build: a `success` result of `code`, `ai`, `stripe`, `frontend`, `infra`, `observability` (mode B) or `cicd` -> `reviewer`; the work-order type decides which of the six
  agents listed in the `NEXT:` line runs (`NEXT: role=reviewer agent=a,b,c,d,e,f` lists all of them). `changes-requested` returns to the author named by the review `role:`
  (`stripe`, `frontend`, `infra`, `observability`, `cicd`; `ai` and no role -> `code`, the same agent for `ai`).
- Two-reviewer tasks (stripe, ai, frontend) run **sequentially**; because the board routes on the latest record, an `approved` of the second reviewer must never mask an earlier
  `changes-requested`: any `changes-requested` returns to the author before the other review runs. **Hold:** right after the first reviewer's `approved`, and before running `board.py`, the orchestrator writes
  the second review work-order with `status: pending` (same `task`); the task's work-orders are set `done` only after the last `approved`. Otherwise
  `{kind: review, outcome: approved, all_tasks: done}` fires `NEXT: orchestrator` (the PR hand-off) after the first review. Each `changes-requested` is one
  `review_rounds` round, so a project may raise `limits.review_rounds` via `openspec/handoff-profile.yaml`.
- All tasks approved and done -> `NEXT: role=orchestrator`: the orchestrator hands the user the commit plan and the PR text; the user pushes and opens the PR. It does not launch any deploy.
- E7: see A5 and A10. Verify roles that fail (`solution-reviewer`, `infrastructure-reviewer`, `sync`, `debug`, `design-reviewer`, `site-verify`) go to the orchestrator
  (the user decides the next move); a failed observability `report` falls to the fallback (`orchestrator`). Order of the final verifies with a front: debugger first, then `static-site-verifier`;
  `NEXT: final-gate` can fire after either `pass` (all tasks done, drift false, no pending delta), so E9 re-checks both verifies before the archive.

## What the profile does not enforce (orchestrator checks by hand)

- `spec_impact` consistent with the `## Spec impact` text (A1).
- `## Functionality` and `## Diagram` in construction work-orders (the protocol requires only the generic sections).
- `role:` present on every record that needs it (`pipeline-ci`/`pipeline-cd`, reviews of non-`code` tasks, `observability-live`/`observability-review`).
- Which of the six agents in the `reviewer` role runs (the work-order type decides).
- That the user, not an agent, merged the PR and released prod (`gh pr view` / `gh run view` evidence under `## Approvals`).
