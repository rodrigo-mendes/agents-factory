# Conventions

These are the rules every artifact in the factory follows. Read them before you add or change a
skill, subagent or rule.

## The workflow: P0 to P5

Every agent works in six phases.

| Phase | Name | What it does |
|---|---|---|
| P0 | Verify docs | Check the official documentation and the version before anything else. |
| P1 | Analyze | Understand the request and the current state. |
| P2 | Consult | Load the skills that match, and ask you only what the sources cannot answer. |
| P3 | Propose | Show a plan. Some agents wait for your approval here. |
| P4 | Implement | Write the output. |
| P5 | Validate | Check the result against the same rules. |

Advisory agents produce designs and plans instead of code. For them P4 means deliver, not
implement.

## Three tiers

Every skill separates its guidance into three tiers.

| Tier | Meaning | Must include |
|---|---|---|
| ✅ Always do | The agent does it without asking. | Working code or an exact command. |
| ⚠️ Ask first | A decision that needs your approval. | A trade-off table. |
| 🚫 Never do | The agent blocks it. | The alternative and the impact. |

## Sources and versions

- **Version absolutism.** One skill is one version. A new version is a new skill. Old versions are
  treated as misinformation.
- **Source hierarchy.** Official documentation or registry first, then an official blog, then
  official examples, then verified community sources. Reject everything else. Reject sources older
  than 12 months unless they describe the current stable release.
- **Executable truth.** Every claim links to a dated official source. Without one, mark it
  *unverified*.

## Naming

All names are kebab-case.

| Artifact | Pattern | Examples |
|---|---|---|
| Knowledge skill | gerund + noun | `researching-technical-frameworks`, `auditing-architecture` |
| Command | action + noun, or domain + role | `skill-creator`, `skill-best-practices-validator` |
| Subagent | domain + role | `framework-researcher`, `artifact-author` |
| Rule | scope + noun | `skill-frontmatter`, `naming-conventions` |

A version-locked skill adds the version with hyphens: `developing-camel-quarkus-core-v3-40`
means Camel Quarkus 3.40. Dots are not allowed in names.

Wrong and right:

| Wrong | Right | Why |
|---|---|---|
| `technical-framework-researcher` as a knowledge skill | `researching-technical-frameworks` | A knowledge skill starts with a gerund. |
| `researcher-framework` | `framework-researcher` | A subagent is domain then role. |
| `conventions-naming` | `naming-conventions` | A rule is scope then noun. |
| `MyNewSkill` | `my-new-skill` | No PascalCase. |

## Skill structure

- Keep `SKILL.md` under 500 lines and link `blueprints/` for the rest. This is progressive
  disclosure: the basics first, the detail on demand.
- A command needs `blueprints/evaluation-scenarios.md`, which the skill evaluator runs.
- Templates live in the `assets/` folder of the skill that owns them. There is no shared
  `templates/` folder, because APM packages only carry skill subfolders.

The header fields are in the [frontmatter cheatsheet](frontmatter-cheatsheet.md).

## Where things live

- **Edit** `packages/<family>/<package>/.apm/`.
- **Never edit** `.claude/`. It is generated by `apm install --target claude` and committed.
- Regenerate after every change. See [Maintaining the docs](maintaining-docs.md).
