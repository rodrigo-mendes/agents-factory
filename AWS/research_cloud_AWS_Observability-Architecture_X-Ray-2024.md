## Executive Summary

AWS X-Ray is a fully managed distributed tracing service that collects data about requests served by your application, providing tools to view, filter, and gain insights into request behavior to identify performance bottlenecks and error root causes. X-Ray receives trace data as segments from your application's compute resources and groups segments sharing a common request into traces. It processes traces to generate a service graph (trace map) — a visual representation of your distributed application's topology showing service nodes, edges (inter-service calls), response times, error rates, and throughput. X-Ray integrates natively with AWS Lambda, Amazon API Gateway, Elastic Load Balancing, Amazon SNS, Amazon SQS, AWS Step Functions, Amazon EventBridge, AWS AppSync, Amazon S3, and Amazon Bedrock AgentCore, providing both active instrumentation (sampling and tracing incoming requests) and passive instrumentation (propagating trace context from upstream services). Trace data and service graph data are retained for 30 days.

The 2024–2026 edition's most architecturally significant developments are: (1) **OpenTelemetry as the strategic instrumentation standard** — AWS X-Ray SDKs and Daemon entered maintenance mode on February 25, 2026, with AWS recommending migration to OpenTelemetry (OTel) SDKs and the CloudWatch Agent or OTel Collector for all new and existing applications; (2) **CloudWatch unified observability integration** — X-Ray traces are now fully integrated into the CloudWatch console via Application Signals, Transaction Search, Trace Map, and correlated metrics/logs/traces views, eliminating the need for the standalone X-Ray console; (3) **Adaptive sampling with anomaly-driven boost** — sampling rules now support `SamplingRateBoost` configuration with `MaxRate` and `CooldownWindowMinutes`, enabling automatic sampling rate increases during anomalies for faster root-cause analysis; (4) **W3C Trace Context support** — X-Ray natively accepts W3C-format trace IDs (formatted in X-Ray trace ID format), enabling interoperability with OpenTelemetry and other W3C-compliant tracing systems; (5) **Resource-based policies** — X-Ray now supports resource-based policies for AWS service integrations (e.g., Amazon SNS active tracing), enabling fine-grained cross-service trace data permissions.

The three most critical architecture guardrails for X-Ray distributed tracing are: (1) **adopt OpenTelemetry instrumentation for all new applications** — the X-Ray SDK/Daemon are in maintenance mode (security fixes only); new development must use OTel SDKs with the CloudWatch Agent or OTel Collector to ensure access to future features and active support; (2) **design sampling rules at the entry point (root service)** — X-Ray sampling is parent-based, meaning the sampling decision is made once by the first X-Ray-enabled service and propagated downstream; rules configured on downstream services will not apply if an upstream parent already made the decision; (3) **use annotations (not metadata) for searchable trace attributes** — annotations are indexed key-value pairs (up to 50 per trace) that enable filter expressions and trace search, while metadata is not indexed; choosing incorrectly means inability to find traces during incident response.

## Cloud Architecture Glossary

```
Term: Trace
Definition: A unique identifier (trace ID) that connects all segments generated by a single client request as it flows through distributed services. A trace collects all segments and subsegments generated by that request, representing the complete end-to-end path. Trace IDs follow the format: 1-{8 hex digits epoch time}-{24 hex digits unique ID} (e.g., 1-5759e988-bd862e3fe1be46a994272793).
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-traces
Architect Usage: A trace represents a single user request's journey through your distributed system. Use trace IDs for cross-service correlation during incident investigation. Every instrumented service in the request path contributes segments to the same trace. Trace data is retained for 30 days.
Common Confusion: A trace is NOT a single log entry or metric data point. It is a collection of segments from multiple services. Also, X-Ray now accepts W3C Trace Context format trace IDs (e.g., 4efaaf4d1e8720b39541901950019ee5 formatted as 1-4efaaf4d-1e8720b39541901950019ee5), but the timestamp component is not required for W3C-origin IDs.

Term: Segment
Definition: A JSON document (up to 64 kB) sent by a compute resource running your application logic that records the resource's name, details about the request it served, details about work done (start/end times, subsegments), and any issues that occurred (errors, faults, exceptions). Segments are the primary data unit sent to X-Ray.
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-segments
Architect Usage: Each service in your application sends one segment per incoming request. The segment captures the service's view of the request — timing, response status, and downstream calls (as subsegments). Design your instrumentation so that every entry point (HTTP handler, Lambda handler, message consumer) creates a segment. Segment names should match the domain name or logical service name.
Common Confusion: A segment is NOT the same as a span in OpenTelemetry. In OTel-to-X-Ray translation, a Server Span becomes an X-Ray segment, while all other span kinds (Client, Internal, Producer, Consumer) become subsegments. When migrating to OTel, this mapping is handled automatically by the X-Ray exporter.

Term: Subsegment
Definition: A subdivision of a segment that records details about downstream calls (AWS SDK calls, external HTTP APIs, SQL queries) or annotates specific code blocks within your application. Subsegments provide granular timing and can be embedded within a segment document or sent independently.
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-subsegments
Architect Usage: Use subsegments to instrument all external dependencies — AWS service calls, HTTP APIs, database queries. For services that don't send their own segments (e.g., DynamoDB), X-Ray generates inferred segments from your subsegments to represent them on the trace map. Independent subsegments (sent separately) are essential for asynchronous workflows and long-running requests where you need to report progress before the parent completes.
Common Confusion: Subsegments from the upstream service and segments from the downstream service represent the SAME call from different perspectives. The trace map uses the downstream service's segment (if available) for node information, but the upstream subsegment for edge information (latency between services includes network transit time).

Term: Service Graph (Trace Map)
Definition: A JSON document (and corresponding visualization) that represents the topology of your distributed application — showing service nodes, their health/performance metrics, and edges representing inter-service calls. Generated by X-Ray from segment and subsegment data. Service graph data is retained for 30 days.
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-servicegraph
Architect Usage: The trace map is the primary diagnostic tool for understanding distributed system behavior. Each node shows: average latency, request rate, and error/fault/throttle percentages. Use the trace map to identify hot paths, detect cascading failures, and understand service dependencies. In the CloudWatch console, the trace map correlates with CloudWatch metrics and logs for unified observability.
Common Confusion: The service graph shows ALL services that contribute segments/subsegments within the selected time range — not just a single trace. Individual trace timelines are viewed separately via Trace Details. The trace map updates as new trace data arrives and reflects the aggregate behavior over the selected time window.

Term: Sampling
Definition: An algorithm applied by the X-Ray SDK (or OpenTelemetry with X-Ray Remote Sampler) to determine which requests get traced. Default: first request each second (reservoir) + 5% of additional requests (fixed rate). Sampling rules are configured centrally in the X-Ray/CloudWatch console and distributed to all instrumented service instances.
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-sampling
Architect Usage: Sampling is PARENT-BASED — the sampling decision is made once by the first X-Ray-enabled service (root service) and propagated to all downstream services via the tracing header. Custom sampling rules on downstream services only apply when they are the root of a NEW trace (e.g., async workers starting new traces). Design sampling rules at the entry point. Use centralized (console-defined) rules over local JSON rules to avoid per-instance reservoir multiplication.
Common Confusion: Sampling rules are NOT per-instance quotas. X-Ray manages a shared reservoir across all instances of a service and assigns per-instance quotas based on the number of reporting instances. If you use local JSON rules, each instance maintains its own independent reservoir, effectively multiplying your intended sample rate by the number of instances.

Term: Annotations
Definition: Simple key-value pairs (string, number, or boolean values — no objects or arrays) attached to segments or subsegments that are INDEXED by X-Ray for use with filter expressions. Maximum 50 annotations per trace. Keys must be alphanumeric (underscores allowed, no other symbols or whitespace).
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-annotations
Architect Usage: Use annotations for attributes you need to SEARCH by — customer_id, order_id, tenant_id, environment, deployment_version. These enable filter expressions like `annotation.customer_id = "C12345"` to find specific traces during incident response. Plan your annotation schema upfront — it's your primary trace search index. In OpenTelemetry, add attribute keys to the `aws.xray.annotations` list to convert them from metadata to annotations.
Common Confusion: Annotations are aggregated at the TRACE level, not per-segment. If multiple segments in a trace set the same annotation key to different values, the behavior is non-deterministic. Annotations are NOT encrypted by SSE even when segment encryption is enabled. Do not put sensitive data (PII, secrets) in annotations.

Term: Metadata
Definition: Key-value pairs with values of ANY type (including objects, arrays, nested structures) attached to segments or subsegments that are NOT indexed by X-Ray. Metadata can be any size within the 64 kB segment document limit. Viewable only via BatchGetTraces API or in segment detail views.
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-metadata
Architect Usage: Use metadata for debugging information you don't need to search by — request/response payloads, configuration snapshots, intermediate computation results. Metadata is stored in the trace but requires knowing the trace ID to retrieve. Keys starting with `AWS.` are reserved for AWS-provided SDKs. In OpenTelemetry, all span attributes convert to metadata by default (unless explicitly added to `aws.xray.annotations`).
Common Confusion: Metadata is NOT searchable via filter expressions. If you put a customer_id in metadata instead of annotations, you cannot find that trace by customer_id. This is the most common instrumentation mistake and causes incident response delays.

Term: Filter Expression
Definition: A query syntax used to search traces by properties including annotations, HTTP URL, response status, duration, service name, and user. Filter expressions enable drilling down from aggregate trace map views to specific traces matching criteria (e.g., `service("api") { fault = true AND responsetime > 5 }`).
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-console-filters.html
Architect Usage: Filter expressions are the primary mechanism for finding specific traces during incidents. Design your annotation schema to support the filter expressions you'll need during incidents — by customer, by error type, by deployment version, by feature flag. Test filter expressions in non-production to validate that your instrumentation supports the queries you need.
Common Confusion: Filter expressions operate on trace summaries (indexed data), NOT on full trace documents. Only annotations, HTTP fields, user, status codes, response time, and a few other indexed fields are searchable. Metadata fields are NOT searchable via filter expressions.

Term: Group
Definition: A named collection of traces matching a filter expression. Groups generate their own service graph, trace summaries, and CloudWatch metrics (published every minute). Groups are identified by name or ARN and can be used to isolate specific workload slices (e.g., "production-errors", "high-latency-requests", "tenant-A").
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-groups
Architect Usage: Use groups to create focused views for different operational concerns — error traces, specific tenants, high-latency requests, canary deployment traffic. Groups generate CloudWatch metrics that can trigger alarms. Groups are billed by the number of retrieved traces matching the filter expression. Updating a group's filter doesn't retroactively change stored data — only subsequent traces are evaluated.
Common Confusion: Groups do NOT partition trace storage. A trace can belong to multiple groups simultaneously if it matches multiple filter expressions. Groups are a QUERY mechanism with metric generation, not a storage or access control boundary.

Term: X-Ray Daemon
Definition: A software application (available for Linux, Windows, macOS) that listens for trace data on UDP port 2000, buffers segment documents in a queue, and uploads them to X-Ray in batches. The daemon is included on AWS Elastic Beanstalk and AWS Lambda platforms. As of February 25, 2026, the daemon entered maintenance mode (security fixes only).
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-daemon.html
Architect Usage: For NEW applications, do NOT use the X-Ray Daemon — use the CloudWatch Agent (v1.300025.0+) or OpenTelemetry Collector with the AWS X-Ray exporter instead. For EXISTING applications still using the daemon, plan migration to the CloudWatch Agent. The daemon requires AWSXRayDaemonWriteAccess IAM permissions (includes PutTraceSegments, GetSamplingRules, GetSamplingTargets).
Common Confusion: The daemon is NOT the X-Ray SDK. The SDK instruments your code and sends segment documents over UDP to the daemon (or CloudWatch Agent). The daemon/agent then batches and uploads to the X-Ray service over HTTPS. Replacing the daemon with CloudWatch Agent does NOT require changing SDK instrumentation — only the trace data receiver changes.

Term: Tracing Header (X-Amzn-Trace-Id)
Definition: An HTTP header containing the trace ID, parent segment ID, and sampling decision that propagates trace context between services. Format: `X-Amzn-Trace-Id: Root=1-{epoch}-{unique};Parent={segment-id};Sampled={0|1}`. The first X-Ray-integrated service adds this header; downstream services propagate it.
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-tracingheader
Architect Usage: The tracing header enables cross-service trace correlation. Ensure your application does NOT strip this header from incoming requests (unless intentionally breaking trace propagation for security isolation). For OpenTelemetry, configure both W3C Trace Context and X-Ray propagators to maintain compatibility with AWS services that only support X-Ray trace headers. The Sampled=1 flag means the request IS being traced; Sampled=0 means it is NOT.
Common Confusion: The tracing header CAN originate from clients (including malicious ones). The X-Forwarded-For-derived client_ip in segments from forwarded requests should NOT be trusted as it can be forged. Consider stripping X-Amzn-Trace-Id from external client requests at your edge (API Gateway/ALB) and letting the edge service generate a fresh trace ID.

Term: AWS Distro for OpenTelemetry (ADOT)
Definition: AWS's supported distribution of the OpenTelemetry project — providing APIs, SDKs, and tools to instrument applications once and send correlated metrics and traces to multiple AWS monitoring solutions including CloudWatch, X-Ray, Amazon OpenSearch Service, and Amazon Managed Service for Prometheus.
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-services-adot.html
Architect Usage: ADOT is the recommended instrumentation path for sending traces to X-Ray. It supports X-Ray Remote Sampling (centralized sampling rules), X-Ray trace context propagation, annotations via `aws.xray.annotations` attribute, and zero-code auto-instrumentation for Java, .NET, Python, and Node.js. Use ADOT when you need AWS-validated, production-ready OpenTelemetry components with X-Ray compatibility.
Common Confusion: ADOT is NOT a separate tracing backend — traces still arrive in X-Ray and are viewed in the CloudWatch console. ADOT is the instrumentation and collection layer. You can also use vanilla OpenTelemetry SDKs with the X-Ray exporter — ADOT simply packages pre-configured, AWS-tested components.

Term: Adaptive Sampling (SamplingRateBoost)
Definition: A sampling rule enhancement that automatically increases the sampling rate during detected anomalies, providing more trace data precisely when debugging is most needed. Configured via MaxRate (maximum sampling rate during anomalies, 0.0–1.0) and CooldownWindowMinutes (minimum time between boosts to prevent continuous elevation).
Provider Docs Section: https://docs.aws.amazon.com/xray/latest/devguide/xray-adaptive-sampling.html
Architect Usage: Enable adaptive sampling on critical path services to automatically capture more traces during error spikes or latency anomalies without permanently increasing sampling costs. Set MaxRate to 0.5 (50%) for most services and CooldownWindowMinutes to 10 to prevent runaway costs. This eliminates the common operational pattern of manually increasing sampling during incidents and forgetting to reduce it afterward.
Common Confusion: Adaptive sampling does NOT replace base sampling rules — it BOOSTS the rate temporarily during anomalies. The base rate applies during normal operation. The boost applies only when X-Ray detects anomalous behavior in the matching service.
```

## Architecture Guardrails

### ✅ Mandatory Patterns

**Use OpenTelemetry Instrumentation for All New Applications**
- Pillar Alignment: Operational Excellence — "Perform operations as code"
- Why: AWS X-Ray SDKs and Daemon entered maintenance mode on February 25, 2026. Only security fixes will be released. OpenTelemetry provides enhanced framework/library instrumentation, zero-code auto-instrumentation for Java/.NET/Python/Node.js, flexible sampling configuration, unified metrics/logs/traces collection, and continued feature development. The CloudWatch console experience remains unchanged — traces appear in the same format via Traces and Trace Map pages.
- AWS Services: AWS Distro for OpenTelemetry (ADOT), CloudWatch Agent (v1.300025.0+), OpenTelemetry Collector with AWS X-Ray Exporter
- Architecture Decision:
  Instrument applications using OpenTelemetry SDKs (or ADOT auto-instrumentation). Configure the OTel Tracer Provider with: X-Ray ID Generator (for X-Ray-compatible trace IDs), X-Ray Remote Sampler (for centralized sampling rules), X-Ray Propagator (for `X-Amzn-Trace-Id` header compatibility with AWS services), and OTLP Exporter targeting the CloudWatch Agent or OTel Collector on ports 4317 (gRPC) or 4318 (HTTP). The collector forwards traces to X-Ray via the `awsxray` exporter.
- Verification:
  After deployment, verify traces appear in CloudWatch console → X-Ray traces → Trace Map. Validate with: `aws xray get-trace-summaries --start-time $(date -d '5 minutes ago' +%s) --end-time $(date +%s)` — should return recent trace summaries from the OTel-instrumented service.
- Trade-offs: Migration requires code changes to replace X-Ray SDK imports with OTel SDK equivalents. OTel SDK configuration is more verbose than X-Ray SDK. Some X-Ray-specific features (e.g., SQL query capture format) may have slight differences in OTel equivalents.
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-sdk-migration.html

---

**Design Sampling Rules at the Entry Point (Root Service)**
- Pillar Alignment: Cost Optimization — "Implement cloud financial management"; Performance Efficiency — "Use resources efficiently"
- Why: X-Ray sampling is parent-based. The sampling decision is made ONCE by the first X-Ray-enabled service that handles the request (the "Root" service). Downstream services honor the upstream sampling decision regardless of their own matching rules. Misconfiguring sampling on downstream services creates the illusion of control while having no effect, wastes configuration effort, and leads to confusion during incidents when expected trace volume doesn't match.
- AWS Services: AWS X-Ray (Sampling Rules), Amazon API Gateway, Elastic Load Balancing (ALB), AWS Lambda
- Architecture Decision:
  Configure sampling rules targeting your root services — typically API Gateway stages, ALB-fronted services, or the first Lambda function in a chain. Use rule priority (1–9999, ascending) to match specific high-value paths first (e.g., priority 1: trace all `/payment/*` requests at 100%), then fall through to lower-priority default rules. Set reservoir sizes at the root to guarantee minimum trace volume. For async workers that start NEW traces (not processing messages from traced upstream services), configure sampling rules targeting those workers specifically.
- Verification:
  In CloudWatch console → X-Ray → Sampling → View sampling results, verify "Total matched rule" counts align with expected request volumes at your entry points. If a rule shows zero matches on a downstream service, it confirms the parent-based decision is already made upstream.
- Trade-offs: Centralizing sampling logic at the entry point requires understanding your full request flow topology. Changes to sampling require updating rules at potentially multiple entry points if you have multiple root services.
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-console-sampling.html

---

**Use Centralized (Console-Defined) Sampling Rules Over Local JSON Configuration**
- Pillar Alignment: Operational Excellence — "Make frequent, small, reversible changes"; Cost Optimization — "Use appropriate services"
- Why: Local JSON sampling rules create per-instance reservoirs that multiply across a fleet — a reservoir of 1 per second across 100 instances means 100 traces/second instead of the intended 1. Centralized rules use X-Ray's managed reservoir that distributes quotas evenly across all instances. Centralized rules can be updated without code redeployment.
- AWS Services: AWS X-Ray (Console Sampling Rules), CloudWatch Agent (TCP port 2000 proxy for sampling API)
- Architecture Decision:
  Define all sampling rules in the CloudWatch console (Settings → X-Ray traces → Sampling rules). Configure the CloudWatch Agent or ADOT to use X-Ray Remote Sampling (the default for ADOT). The CloudWatch Agent acts as a local proxy on TCP port 2000 for sampling API calls. Remove any local `sampling-rules.json` files from application code. Use sampling rule options: Rule name, Priority (1–9999), Reservoir (guaranteed traces/sec), Rate (% beyond reservoir), Service name, Service type, Host, HTTP method, URL path, Resource ARN.
- Verification:
  `aws xray get-sampling-rules` — verify rules are defined. Check that no local sampling JSON files exist in deployed application artifacts. Verify CloudWatch Agent is listening on port 2000: `netstat -tlnp | grep 2000`.
- Trade-offs: Requires network connectivity from application instances to the X-Ray sampling API (via CloudWatch Agent proxy). Adds a dependency on the sampling API availability — if unreachable, SDKs fall back to default (1 req/sec + 5%).
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-console-sampling.html

**Enable Trace Encryption with AWS KMS**
- Pillar Alignment: Security — "Protect data in transit and at rest"
- Why: Trace data may contain request URLs, HTTP headers, database queries, service responses, and custom annotations/metadata that include business-sensitive or PII data. X-Ray encrypts all trace data by default with an AWS-owned key, but using a customer managed KMS key (CMK) provides audit trail via CloudTrail, key rotation control, and the ability to revoke access to historical trace data.
- AWS Services: AWS X-Ray (Encryption Configuration), AWS KMS
- Architecture Decision:
  For production workloads handling sensitive data, configure X-Ray encryption with a customer managed KMS key via `PutEncryptionConfig`. Ensure the KMS key policy grants `kms:CreateGrant` and `kms:DescribeKey` to administrators, and `kms:Decrypt` to users who need to read trace data. Use `AWSXrayFullAccess` or explicitly grant `xray:PutEncryptionConfig` only to administrators — not to application roles.
- Verification:
  `aws xray get-encryption-config` — verify `Type` is `KMS` and `KeyId` is your CMK ARN (not `aws/xray` which is the AWS managed key). Verify KMS key policy includes X-Ray service grants.
- Trade-offs: Customer managed key adds KMS API call costs and a dependency on key availability. If the key is deleted or access is revoked, historical trace data becomes unreadable. Users need `kms:Decrypt` permission in addition to X-Ray read permissions.
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-console-encryption.html

---

**Instrument All Service Boundaries with Trace Context Propagation**
- Pillar Alignment: Reliability — "Monitor end-to-end tracing of requests through your system" (REL06-BP07)
- Why: Distributed tracing only provides value when trace context is propagated across ALL service boundaries. A single un-instrumented service breaks the trace into disconnected fragments, making root-cause analysis impossible for requests that traverse the gap. The AWS Well-Architected Reliability Pillar explicitly requires end-to-end request tracing.
- AWS Services: AWS X-Ray, ADOT, CloudWatch Agent, API Gateway (Active Tracing), Lambda (Active Tracing), ALB (Request Tracing)
- Architecture Decision:
  Enable active tracing on all AWS service entry points: API Gateway stages (X-Ray tracing enabled), Lambda functions (`TracingConfig.Mode = Active`), Step Functions state machines. For custom services, ensure the OTel SDK is configured with both W3C Trace Context and X-Ray propagators. For message-based architectures (SQS, SNS, EventBridge), ensure the tracing header is propagated via message system attributes. For HTTP services, verify `X-Amzn-Trace-Id` and/or `traceparent` headers are forwarded (not stripped) by proxies and API gateways.
- Verification:
  In the CloudWatch Trace Map, verify there are no "unknown" or disconnected nodes. Select a trace and verify the timeline shows a continuous span tree from entry to all leaves without gaps. Run an end-to-end test request and confirm a single trace ID appears across all services.
- Trade-offs: Full instrumentation adds slight latency overhead (typically <1ms per service for SDK processing). Every service needs instrumentation configuration and IAM permissions for X-Ray. Services using custom protocols (non-HTTP, non-AWS SDK) require manual context propagation.
- Source: https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_monitor_aws_resources_end_to_end.html

---

**Use Annotations for Searchable Business Context**
- Pillar Alignment: Operational Excellence — "Anticipate failure"; Reliability — "Monitor workload resources"
- Why: During incidents, the first question is "which customers/transactions are affected?" Without indexed annotations, you cannot search traces by business identifiers (customer_id, order_id, tenant_id). Metadata is NOT indexed and NOT searchable via filter expressions. Putting business identifiers in metadata instead of annotations transforms a 30-second trace lookup into an impossible needle-in-a-haystack search across 30 days of unindexed data.
- AWS Services: AWS X-Ray (Annotations, Filter Expressions)
- Architecture Decision:
  Define a standard annotation schema for your organization. At minimum, annotate: `customer_id` (or `tenant_id` for multi-tenant), `environment` (prod/staging/dev), `deployment_version`, and one domain-specific identifier (order_id, session_id, etc.). In OpenTelemetry, add these keys to the `aws.xray.annotations` span attribute list. Limit to 50 annotations per trace (hard limit). Use string, number, or boolean values only — no objects or arrays. Keys must be alphanumeric with underscores.
- Verification:
  In CloudWatch console → X-Ray traces, use a filter expression like `annotation.customer_id = "test-customer"` to verify annotations are indexed and searchable. `aws xray get-trace-summaries --filter-expression 'annotation.environment = "production"'` should return results.
- Trade-offs: Annotations are limited to 50 per trace and must be simple scalar values. Annotation keys cannot be changed after trace submission — schema evolution requires updating instrumentation code. Annotations are NOT encrypted by SSE (even when trace encryption is enabled) — do not annotate with PII directly.
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-annotations

### ⚠️ Architectural Decisions

**Instrumentation Strategy: OpenTelemetry SDK vs ADOT Auto-Instrumentation vs CloudWatch Application Signals**

- Options:

  | Option | AWS Service/Tool | Optimizes | Sacrifices | Best When |
  |--------|-----------------|-----------|------------|-----------|
  | OpenTelemetry SDK (Manual) | OTel SDK + CloudWatch Agent | Full control, custom spans, precise annotations | Requires code changes per service | You need custom subsegments, specific annotation placement, or use unsupported languages/frameworks |
  | ADOT Auto-Instrumentation | ADOT Java/.NET/Python/Node.js Agent | Zero-code instrumentation, fast onboarding | Less control over span granularity | Standard web frameworks (Spring Boot, Express, Django, ASP.NET) with standard AWS SDK usage |
  | CloudWatch Application Signals | Application Signals Lambda Layer or EKS/ECS addon | SLI/SLO monitoring, service health dashboards, correlated metrics | Limited to supported runtimes, AWS-opinionated observability | You want AWS-managed SLI/SLO dashboards with minimal configuration overhead |

- Cost Profile: All options send traces to X-Ray at the same per-trace pricing. ADOT and Application Signals may generate additional CloudWatch metrics. Auto-instrumentation captures more spans by default, potentially increasing trace volume (and cost) if sampling is not tuned.
- Lock-in Assessment: OTel SDK is fully portable (CNCF standard). ADOT adds AWS-specific components but core instrumentation is standard OTel. Application Signals is AWS-specific and not portable.
- Architect Instruction: "Ask whether the team has existing OpenTelemetry expertise and whether they need custom trace annotation placement before choosing between manual SDK and auto-instrumentation."
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-instrumenting-your-app.html

**Trace Data Collection: CloudWatch Agent vs OpenTelemetry Collector**

- Options:

  | Option | AWS Service/Tool | Optimizes | Sacrifices | Best When |
  |--------|-----------------|-----------|------------|-----------|
  | CloudWatch Agent | CloudWatch Agent (v1.300025.0+) | Single agent for metrics + logs + traces, AWS-managed, supports X-Ray sampling proxy (port 2000), minimal configuration | Less flexibility in pipeline processing, AWS-centric | AWS-only deployments, teams preferring managed simplicity, already using CloudWatch Agent for metrics/logs |
  | OpenTelemetry Collector | OTel Collector (contrib distribution) | Multi-backend export, tail sampling, custom processors, pipeline flexibility | More configuration complexity, self-managed, requires `awsproxy` extension for X-Ray sampling | Multi-cloud/hybrid environments, need tail sampling, need to export to multiple backends (X-Ray + Jaeger + Datadog) |

- Cost Profile: Both are free to run (open source). CloudWatch Agent is AWS-managed with automatic updates via SSM. OTel Collector requires self-managed updates and monitoring of the collector itself.
- Lock-in Assessment: CloudWatch Agent is AWS-specific. OTel Collector is CNCF-standard and fully portable — swap the exporter to send traces to any backend.
- Architect Instruction: "Ask whether traces need to be sent to non-AWS backends (Datadog, Jaeger, Grafana Tempo) or if tail sampling is required before choosing the collector."
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-sdk-migration.html

---

**Sampling Strategy: Conservative Default vs Aggressive Debug vs Adaptive**

- Options:

  | Option | Configuration | Optimizes | Sacrifices | Best When |
  |--------|--------------|-----------|------------|-----------|
  | Conservative (Default) | Reservoir: 1, Rate: 5% | Cost efficiency, low overhead | May miss rare errors, limited debugging data | High-traffic production with predictable behavior |
  | Targeted High-Rate | Reservoir: 10, Rate: 50-100% on specific paths | Complete visibility on critical paths | Higher cost, more storage | Payment flows, authentication, order processing — paths where every failure matters |
  | Adaptive Boost | Base: 5%, MaxRate: 50%, Cooldown: 10min | Automatic detail during anomalies, cost-efficient during normal operation | Slight delay before boost activates, cost spikes during incidents | Services with variable error rates where you need automatic observability scaling |

- Cost Profile: X-Ray pricing is per trace scanned/recorded. Conservative: ~$5/million traces. High-rate on critical paths: budget for 10-20x base cost on those paths. Adaptive: cost between conservative and high-rate, spiky during incidents.
- Architect Instruction: "Ask what the acceptable trace loss rate is for critical business transactions and what the monthly tracing budget is before designing sampling rules."
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-console-sampling.html

---

**Trace Context Propagation: X-Ray Header Only vs W3C + X-Ray Dual Propagation**

- Options:

  | Option | Propagation Format | Optimizes | Sacrifices | Best When |
  |--------|-------------------|-----------|------------|-----------|
  | X-Ray Header Only | `X-Amzn-Trace-Id` | Full AWS service compatibility, simpler configuration | Not compatible with non-AWS services using W3C Trace Context | Pure AWS architecture, all services use X-Ray or ADOT |
  | W3C + X-Ray Dual | `traceparent` + `X-Amzn-Trace-Id` | Interoperability with non-AWS services, standard compliance, multi-cloud readiness | Slightly more configuration, two headers to manage | Hybrid architectures, multi-cloud, services calling external APIs that support W3C Trace Context |

- Cost Profile: No cost difference — propagation is header-level only.
- Lock-in Assessment: X-Ray-only is AWS-locked. W3C + X-Ray is portable and future-proof.
- Architect Instruction: "Ask whether any services in the request path are non-AWS or use non-ADOT OpenTelemetry instrumentation that expects W3C traceparent headers."
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-tracingheader

### 🚫 Anti-Patterns

**Using X-Ray SDK for New Application Development**
- Risk Level: HIGH
- Why: Operational Excellence pillar violation. AWS X-Ray SDKs entered maintenance mode on February 25, 2026. Only security patches will be released — no new features, no bug fixes (unless security-related), no new language/framework support. Applications built on X-Ray SDK will accumulate technical debt as OpenTelemetry becomes the sole supported instrumentation path.
- Instead: Use OpenTelemetry SDKs (manual instrumentation) or ADOT auto-instrumentation agents. Configure the X-Ray ID Generator, X-Ray Remote Sampler, and X-Ray Propagator for full X-Ray backend compatibility. Replace the X-Ray Daemon with CloudWatch Agent or OpenTelemetry Collector.
- Detection: Search application dependencies for `aws-xray-sdk` (Python), `aws-xray-sdk-core` (Java), `aws-xray-sdk` (Node.js), `AWSXRayRecorder` (.NET). If present in new services (created after Feb 2026), flag for migration.
- Impact: Technical debt accumulation | Future feature inaccessibility | Eventual end-of-support risk
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-sdk-migration.html

---

**Configuring Sampling Rules on Downstream Services Expecting Them to Override Upstream Decisions**
- Risk Level: HIGH
- Why: Cost Optimization and Operational Excellence violation. X-Ray sampling is parent-based — downstream services honor the sampling decision made by the upstream parent service. Sampling rules on Service B will NEVER apply if Service B is always called by an already-traced request from Service A. This creates a false sense of control and leads to unexpected costs (if upstream samples more) or missing data (if architect expects downstream rules to increase sampling).
- Instead: Configure sampling rules at the ROOT service (the first X-Ray-enabled service in the request path). For async workers that start NEW traces, configure rules on the worker. Validate with sampling statistics that rules are actually matching.
- Detection: Review sampling rules targeting services that are never the entry point. Check "Total matched rule" in sampling statistics — if consistently zero for a rule on a downstream service, the rule is ineffective.
- Impact: Cost overrun (unexpected trace volume) | Missing trace data (expected rules not applying) | Operational confusion
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-console-sampling.html

---

**Putting Searchable Business Identifiers in Metadata Instead of Annotations**
- Risk Level: CRITICAL
- Why: Operational Excellence violation — "Anticipate failure." Metadata is NOT indexed and NOT searchable via filter expressions. During an incident, the inability to search traces by customer_id, order_id, or transaction_id transforms a 30-second diagnosis into an hours-long manual trace review. This directly impacts mean-time-to-resolution (MTTR).
- Instead: Use annotations for any attribute you need to search/filter by during incident response. Reserve metadata for large objects, debug payloads, and data you only need when you already know the trace ID. Define an annotation schema standard for your organization.
- Detection: Review instrumentation code for calls to `putMetadata()` or metadata span attributes containing identifiers like `*_id`, `*_key`, `*_code`. If these are not also in annotations (or `aws.xray.annotations`), flag.
- Impact: Incident response delays | Increased MTTR | Inability to assess blast radius during outages
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-annotations

---

**Running Both X-Ray Daemon and CloudWatch Agent/OTel Collector on the Same Port**
- Risk Level: HIGH
- Why: Reliability violation. Both the X-Ray Daemon and CloudWatch Agent/OTel Collector use port 2000 (TCP for sampling proxy) and the OTLP ports 4317/4318. Running both simultaneously causes port conflicts, trace data loss, and unpredictable behavior where some traces are collected by one agent and some by the other.
- Instead: Stop the X-Ray Daemon process BEFORE starting the CloudWatch Agent or OTel Collector. On ECS, remove the X-Ray Daemon sidecar container from task definitions before adding the CloudWatch Agent container. On Elastic Beanstalk, disable X-Ray Daemon via `XRayEnabled: false` before adding CloudWatch Agent `.ebextensions`.
- Detection: `netstat -tlnp | grep 2000` — if two processes are bound (or attempting to bind) to port 2000, there's a conflict. Check container logs for "address already in use" errors.
- Impact: Trace data loss | Inconsistent trace collection | Service startup failures
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-sdk-migration.html

---

**Exposing X-Ray PutTraceSegments Permission to Untrusted Code**
- Risk Level: HIGH
- Why: Security pillar violation. Any entity with `xray:PutTraceSegments` permission can send segments with ANY service name. A compromised or malicious service could inject fake trace segments that pollute the trace map, create misleading service nodes, generate false performance data, or mask real failures behind fabricated healthy segments.
- Instead: Apply least-privilege IAM — only grant `xray:PutTraceSegments` to service roles that legitimately send trace data. Use `AWSXRayDaemonWriteAccess` managed policy (which includes PutTraceSegments, GetSamplingRules, GetSamplingTargets) only for compute roles running instrumented applications. Never attach this policy to user-facing roles or Lambda functions that don't need to send trace data.
- Detection: IAM Access Analyzer — check for roles with `xray:PutTraceSegments` that don't correspond to instrumented compute resources. Review IAM policies for wildcard `xray:*` grants.
- Impact: Trace data integrity compromise | Misleading service maps | Delayed incident detection due to fabricated healthy data
- Source: https://docs.aws.amazon.com/xray/latest/devguide/security_iam_service-with-iam.html

---

**Not Stripping X-Amzn-Trace-Id from External Client Requests**
- Risk Level: MEDIUM
- Why: Security pillar violation. The `X-Amzn-Trace-Id` header can originate from external clients. If not stripped at the edge, attackers can inject trace IDs to: (1) correlate their requests across your internal services, (2) set `Sampled=1` to force tracing of all their requests (bypassing your sampling rules and increasing costs), (3) use predictable trace IDs to test timing-based attacks.
- Instead: Configure your edge service (API Gateway, ALB, CloudFront) to strip or regenerate the `X-Amzn-Trace-Id` header from external requests. API Gateway with active tracing enabled will generate a new trace ID, effectively overriding client-provided values. For ALB, the ALB adds its own tracing header to requests before forwarding.
- Detection: Send a test request with a custom `X-Amzn-Trace-Id` header from outside your infrastructure and check if that exact trace ID appears in X-Ray traces. If it does, your edge is not regenerating trace IDs.
- Impact: Cost manipulation (forced sampling) | Information disclosure (request correlation) | Security boundary violation
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-tracingheader

---

**Exceeding 50 Annotations Per Trace Without Priority Schema**
- Risk Level: MEDIUM
- Why: Performance Efficiency violation. X-Ray indexes a maximum of 50 annotations per trace. If your instrumentation adds annotations without coordination across services, a deep trace (many services) can exceed the limit, silently dropping later annotations. The dropped annotations are typically from downstream services — precisely where you need them most during cascading failure analysis.
- Instead: Define an annotation budget per service tier (e.g., entry point: 10 annotations, middleware: 5, leaf services: 3). Use a shared annotation schema document. For high-cardinality data that doesn't need search, use metadata. Prioritize annotations that support incident response filter expressions.
- Detection: Use `BatchGetTraces` API to retrieve full trace documents and count annotations across all segments. If consistently at 50, some annotations are being dropped.
- Impact: Missing search capability for downstream services | Inconsistent trace searchability | Incident response blind spots
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-concepts.html#xray-concepts-annotations

## Cloud-Native Design Patterns

**Distributed Tracing for Microservices (Service Mesh Observability)**
- Category: Communication | Observability
- Problem: In a microservices architecture with dozens of services, identifying which service caused a latency spike or error in an end-to-end request requires correlating behavior across all services in the request path.
- Solution on AWS:
  Instrument each microservice with OpenTelemetry SDK (or ADOT auto-instrumentation). Configure X-Ray propagator for trace context propagation via `X-Amzn-Trace-Id` header. Deploy CloudWatch Agent as a sidecar (ECS/EKS) or daemon (EC2) to collect and forward traces. Enable active tracing on API Gateway and ALB at the entry point. Use the CloudWatch Trace Map to visualize service topology, latency percentiles, and error rates per edge. Define X-Ray Groups for critical paths (e.g., "checkout-flow") to generate dedicated CloudWatch metrics and alarms.
- Services Used: AWS X-Ray (backend), CloudWatch Agent (collector), ADOT SDK (instrumentation), API Gateway (entry tracing), ALB (request tracing header), CloudWatch (visualization and alarms)
- When to Apply: Any system with >3 services in a request path where end-to-end latency and error attribution matter for SLA compliance.
- When NOT to Apply: Monolithic applications with a single service — standard APM/logging is sufficient. Systems where all calls are fire-and-forget (no request-response chain to trace).
- Trade-offs:

  | Dimension | Benefit | Cost |
  |-----------|---------|------|
  | Observability | Full request path visibility, latency attribution per service | Instrumentation effort per service, sampling trade-offs |
  | Performance | <1ms overhead per service hop | Slight memory/CPU for SDK and agent |
  | Cost | Targeted debugging reduces MTTR | Per-trace pricing, agent compute resources |

- Complements: Circuit Breaker (correlate trace errors with circuit state), Retry with Backoff (trace retry attempts as separate subsegments)
- Source: https://docs.aws.amazon.com/prescriptive-guidance/latest/performance-engineering-aws/tracing.html

---

**Async Trace Correlation (Event-Driven Architecture Tracing)**
- Category: Communication | Data
- Problem: In event-driven architectures (SNS → SQS → Lambda), trace context can be lost between the producer and consumer if the messaging system doesn't propagate the tracing header, breaking the end-to-end trace.
- Solution on AWS:
  When publishing to SNS/SQS from an instrumented service, the X-Ray SDK (or OTel with X-Ray propagator) automatically includes the trace header as a message system attribute (`AWSTraceHeader`). SNS and SQS passively propagate this header to subscribers/consumers. Lambda with active tracing enabled reads the `AWSTraceHeader` from the SQS message and continues the trace. For non-Lambda consumers, read the `AWSTraceHeader` system attribute from the message and set it as the parent context in your tracer. For EventBridge, instrumented publishers include trace context that event targets receive.
- Services Used: Amazon SQS (AWSTraceHeader system attribute), Amazon SNS (passive instrumentation), AWS Lambda (active tracing with SQS event source), Amazon EventBridge (trace header propagation)
- When to Apply: Any architecture using message queues or event buses where end-to-end trace correlation across async boundaries is required.
- When NOT to Apply: Fire-and-forget notifications where the consumer's behavior is irrelevant to the producer's trace. Batch processing systems where individual message traces are not meaningful.
- Trade-offs:

  | Dimension | Benefit | Cost |
  |-----------|---------|------|
  | Observability | Continuous trace across async boundaries | Requires all producers/consumers to be instrumented |
  | Complexity | Single trace shows full event-driven flow | Message replay/retry creates duplicate trace segments |
  | Latency attribution | Queue wait time visible in trace timeline | Queue time may dominate trace duration, obscuring processing latency |

- Complements: Dead Letter Queue (DLQ traces show failure path), CQRS (trace read vs write paths separately), Saga Pattern (trace compensation steps)
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-services-sqs.html

---

**Canary Deployment Trace Isolation**
- Category: Resilience | Migration
- Problem: During canary deployments, you need to compare trace data between the canary (new version) and baseline (current version) to detect regressions before full rollout — but both versions produce traces in the same X-Ray account.
- Solution on AWS:
  Add a `deployment_version` annotation to all traces from your service (set at application startup from environment variable or deployment metadata). Create X-Ray Groups with filter expressions: `annotation.deployment_version = "v2.1.0-canary"` and `annotation.deployment_version = "v2.0.0-baseline"`. Compare CloudWatch metrics generated by each group — latency percentiles, error rates, fault counts. Set CloudWatch Alarms on the canary group's error rate metric to trigger automatic rollback via CodeDeploy.
- Services Used: AWS X-Ray (Annotations, Groups, Filter Expressions), Amazon CloudWatch (Metrics from Groups, Alarms), AWS CodeDeploy (Rollback triggers)
- When to Apply: Any canary or blue-green deployment where trace-level regression detection is needed beyond aggregate metrics.
- When NOT to Apply: Simple A/B tests where business metrics (conversion rate) matter more than per-request latency/error behavior.
- Trade-offs:

  | Dimension | Benefit | Cost |
  |-----------|---------|------|
  | Safety | Per-request regression detection before full rollout | Consumes annotation budget (1 of 50) |
  | Automation | Alarm-driven rollback on trace-detected regressions | Group metric publishing has ~1 minute delay |
  | Visibility | Side-by-side trace comparison between versions | Requires disciplined annotation on every service |

- Complements: Feature Flags (annotate feature flag state for A/B trace analysis), Circuit Breaker (trace circuit state changes during canary)
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-console-groups.html

---

**Multi-Account Cross-Account Tracing**
- Category: Scalability | Communication
- Problem: In AWS Organizations with multiple accounts (production, shared services, data processing), a single request may traverse services in different accounts. Without cross-account tracing, the trace breaks at account boundaries.
- Solution on AWS:
  Configure X-Ray resource-based policies in the receiving account to allow `xray:PutTraceSegments` from the sending account's services. Use IAM conditions (`aws:SourceAccount`, `aws:SourceArn`) to restrict which accounts and resources can send trace data. Ensure the tracing header (`X-Amzn-Trace-Id`) is propagated across account boundaries via HTTP headers or message attributes. In the CloudWatch console, enable cross-account observability to view traces spanning multiple accounts in a single monitoring account.
- Services Used: AWS X-Ray (Resource-based Policies), AWS IAM (Cross-account roles), CloudWatch (Cross-account observability)
- When to Apply: Multi-account AWS Organizations architectures where requests cross account boundaries (shared services account, dedicated workload accounts).
- When NOT to Apply: Single-account deployments. Architectures where account boundaries represent hard security isolation (e.g., separate customer tenants in different accounts where cross-visibility is undesired).
- Trade-offs:

  | Dimension | Benefit | Cost |
  |-----------|---------|------|
  | Visibility | Complete end-to-end trace across accounts | Resource policy management complexity |
  | Security | Controlled via IAM conditions | Requires trust between accounts for trace data |
  | Operations | Single pane of glass in monitoring account | Cross-account CloudWatch setup overhead |

- Complements: Landing Zone (standardize X-Ray resource policies across accounts), Hub-Spoke Networking (trace follows network path)
- Source: https://docs.aws.amazon.com/xray/latest/devguide/security_iam_service-with-iam.html

## Security Architecture

**Identity & Access Management for X-Ray**
- AWS Services:
  - AWS IAM (identity-based policies for X-Ray actions)
  - AWS X-Ray (resource-based policies for service integrations)
  - AWS KMS (encryption key management for trace data)
- Architecture:
  Three tiers of access: (1) **Write access** (`AWSXRayDaemonWriteAccess` managed policy) — for compute roles running instrumented applications; includes `xray:PutTraceSegments`, `xray:GetSamplingRules`, `xray:GetSamplingTargets`; (2) **Read access** (`AWSXrayReadOnlyAccess` managed policy) — for operators and dashboards; includes `xray:GetTraceSummaries`, `xray:BatchGetTraces`, `xray:GetServiceGraph`, `xray:GetGroup`; (3) **Full access** (`AWSXrayFullAccess` managed policy) — for administrators; includes encryption configuration (`PutEncryptionConfig`), sampling rule management, group management. Resource-based policies control which AWS services (e.g., SNS, Lambda) can send trace data to X-Ray with `aws:SourceAccount` and `aws:SourceArn` conditions.
- Configuration Essentials:
  Never grant `xray:*` wildcard to application roles. Use managed policies as the baseline. For custom policies, scope to specific actions needed. Sampling rule ARNs can be used for resource-level permissions on `CreateSamplingRule`, `UpdateSamplingRule`, `DeleteSamplingRule`. Group ARNs support resource-level permissions on `CreateGroup`, `GetGroup`, `UpdateGroup`, `DeleteGroup`.
- Verification:
  IAM Access Analyzer — verify no unintended principals have `xray:PutTraceSegments`. Review resource-based policies: `aws xray get-resource-policy`. Verify compute roles use managed policies: `aws iam list-attached-role-policies --role-name <app-role>`.
- Compliance Alignment: SOC 2 (logical access controls), HIPAA (access to PHI in trace data), PCI-DSS (least privilege for cardholder data environments)
- Source: https://docs.aws.amazon.com/xray/latest/devguide/security_iam_service-with-iam.html

---

**Data Protection for Trace Data**
- AWS Services:
  - AWS X-Ray (server-side encryption at rest)
  - AWS KMS (customer managed keys for trace encryption)
  - VPC Endpoints (PrivateLink for X-Ray API access without internet traversal)
- Architecture:
  X-Ray encrypts ALL trace data at rest by default (AWS-owned key). Optionally configure customer managed KMS key for audit trail and access revocation capability. Trace data in transit is encrypted via TLS (HTTPS) for all X-Ray API calls. For private network access, configure VPC Interface Endpoint for X-Ray (`com.amazonaws.{region}.xray`) to keep trace data within the VPC — no internet gateway required. Annotations are NOT encrypted by SSE — only the segment body. Do NOT put PII in annotations; use metadata (which is encrypted) or tokenize identifiers before annotation.
- Configuration Essentials:
  - Encryption: `aws xray put-encryption-config --type KMS --key-id <CMK-ARN>`
  - VPC Endpoint: Create interface endpoint for `com.amazonaws.{region}.xray` in application VPC
  - Key Policy: Grant `kms:CreateGrant`, `kms:DescribeKey` to encryption administrators; `kms:Decrypt` to trace readers
- Verification:
  `aws xray get-encryption-config` — verify Type=KMS. `aws ec2 describe-vpc-endpoints --filters "Name=service-name,Values=com.amazonaws.*.xray"` — verify VPC endpoint exists. CloudTrail — verify KMS key usage events for X-Ray encryption/decryption.
- Compliance Alignment: HIPAA (encryption at rest for PHI), PCI-DSS (encryption of cardholder data), SOC 2 (data protection controls)
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-console-encryption.html

## Operational Patterns

**Observability Stack Integration (Metrics + Logs + Traces Correlation)**
- AWS Services:
  - AWS X-Ray (distributed traces)
  - Amazon CloudWatch Metrics (service-level metrics from X-Ray Groups)
  - Amazon CloudWatch Logs (correlated log groups)
  - CloudWatch Application Signals (SLI/SLO monitoring)
  - CloudWatch Synthetics (canary-generated traces)
  - CloudWatch RUM (real-user traces from browser)
- Architecture:
  X-Ray traces correlate with CloudWatch Logs via the `aws.cloudwatch_logs` segment field (log group ARN). The CloudWatch console provides a unified view: click a trace to see correlated logs for that request. X-Ray Groups generate CloudWatch metrics (trace count, latency, error rate) published every minute — use these for alarms. Application Signals provides pre-built SLI/SLO dashboards from OTel instrumentation. CloudWatch RUM generates traces from browser sessions that connect to backend X-Ray traces for full client-to-server visibility. CloudWatch Synthetics canaries generate traces for synthetic monitoring that appear on the trace map alongside real traffic.
- Cost Profile: Medium — X-Ray per-trace pricing + CloudWatch metrics (from Groups) + CloudWatch Logs. Primary cost driver is trace volume (controlled by sampling) and log retention period.
- Automation:
  Automate: CloudWatch Alarms on X-Ray Group metrics (error rate > threshold → SNS → PagerDuty). Automate: Sampling rule updates via API during incidents (temporarily increase rate). Manual: Root-cause analysis using trace timelines and correlated logs. Manual: Sampling rule design decisions (which paths to trace at what rate).
- Runbook Skeleton:
  1. Detection: CloudWatch Alarm fires on X-Ray Group metric (e.g., "checkout-flow" error rate > 5%)
  2. Triage: Open CloudWatch Trace Map → identify the erroring node → drill to traces
  3. Filter: Use filter expression `service("checkout-service") { fault = true }` to find error traces
  4. Diagnose: Open trace timeline → identify failing subsegment → view exception stack trace
  5. Correlate: Click "View logs" on the failing segment → see application logs for that request
  6. Resolve: Identify root cause (downstream timeout, bad deployment, data issue)
  7. Post-mortem: Export trace IDs for affected requests, calculate blast radius via annotation filters
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-services-cloudwatch.html

---

**Performance Analysis and Latency Attribution**
- AWS Services:
  - AWS X-Ray (Trace timeline, Service graph latency data)
  - CloudWatch (Trace Map with latency percentiles)
  - X-Ray Groups (segment latency-filtered groups)
- Architecture:
  Use the trace map to identify the highest-latency edges in your service topology. Create X-Ray Groups for slow requests: `responsetime > 3` (traces taking >3 seconds). Drill into slow traces to identify the subsegment contributing most latency (the "critical path"). Compare subsegment timing between normal and slow traces to isolate whether the issue is: network (gap between subsegments), processing (segment self-time), or downstream (subsegment duration). Use annotations to correlate latency with business dimensions (tenant, region, payload size).
- Cost Profile: Low — uses existing trace data. No additional cost beyond base X-Ray pricing. Group metrics add minimal CloudWatch costs.
- Automation:
  Automate: Alarm on P99 latency via X-Ray Group metric. Automate: Periodic comparison of trace map latency between deployments. Manual: Deep-dive into individual slow traces for root cause. Manual: Decision to optimize (caching, connection pooling, async offload) based on trace analysis.
- Source: https://docs.aws.amazon.com/prescriptive-guidance/latest/performance-engineering-aws/tracing.html

---

**Incident Response with Distributed Tracing**
- AWS Services:
  - AWS X-Ray (Filter expressions, Trace details, Groups)
  - CloudWatch (Alarms, Trace Map, correlated logs)
- Architecture:
  Pre-configure X-Ray Groups for incident response: "all-errors" (`{ fault = true OR error = true }`), "high-latency" (`responsetime > 5`), "by-customer" (use annotation-based filter). During incidents: (1) Open Trace Map — identify which service node shows degraded health (red/yellow). (2) Click the degraded node — view error/fault/throttle percentages. (3) Drill to traces — use filter expressions to narrow by time window, error type, customer. (4) Open trace timeline — identify the failing subsegment and its exception details. (5) Cross-reference with annotations to determine blast radius (which customers affected). (6) Use trace IDs to search correlated CloudWatch Logs for full application context.
- Cost Profile: Low — reads existing trace data. Group metrics are the only additional ongoing cost.
- Automation:
  Automate: Alarm → trigger Lambda → query X-Ray for affected trace count → post to incident channel with blast radius estimate. Manual: Root cause determination from trace timelines. Manual: Customer communication decisions based on annotation-filtered affected customer count.
- Runbook Skeleton:
  1. Alert received: "checkout-flow error rate > 5%"
  2. Blast radius: `aws xray get-trace-summaries --filter-expression 'annotation.flow = "checkout" AND fault = true' --start-time <incident-start>` → count unique `annotation.customer_id` values
  3. Root cause: Open highest-frequency error trace → identify failing subsegment → read exception
  4. Mitigation: If downstream dependency → enable circuit breaker / failover
  5. Communication: Report affected customer count and estimated resolution
  6. Post-mortem: Export trace evidence with trace IDs
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-console-filters.html

## Reference Architectures

**Serverless Distributed Tracing (API Gateway → Lambda → DynamoDB/SQS)**
- Context: Serverless API workload with synchronous and asynchronous processing paths
- Services Composition:

  | Layer | Service | Purpose |
  |-------|---------|---------|
  | Entry & Sampling | API Gateway (Active Tracing) | Root service, sampling decision, trace ID generation |
  | Compute | Lambda (Active Tracing) | Application logic, creates segments automatically |
  | Trace Collection | Lambda X-Ray integration (built-in) | Sends segments without daemon |
  | Downstream Tracing | OTel SDK / ADOT auto-instrumentation | Subsegments for DynamoDB, SQS, external API calls |
  | Async Correlation | SQS (AWSTraceHeader attribute) | Propagates trace context to async consumers |
  | Visualization | CloudWatch Trace Map | Service topology and health |
  | Alerting | X-Ray Groups + CloudWatch Alarms | Error rate monitoring per API path |

- Key Decisions: (1) Lambda active tracing auto-creates segments — no daemon needed, but OTel SDK still recommended for custom annotations and subsegments. (2) For Lambda with SQS event source, Lambda automatically reads `AWSTraceHeader` from messages to continue the trace. (3) API Gateway sampling decision applies to the entire downstream trace — configure sampling rules targeting the API Gateway stage.
- Scaling Path: At high scale (>10K RPS), adjust sampling to 1-5% to control X-Ray costs. Use adaptive sampling to automatically increase during anomalies. Consider X-Ray Groups per API path for focused alerting rather than tracing everything.
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-services-lambda.html

**Containerized Microservices Tracing (ECS/EKS with CloudWatch Agent Sidecar)**
- Context: Containerized microservices on ECS or EKS requiring distributed tracing
- Services Composition:

  | Layer | Service | Purpose |
  |-------|---------|---------|
  | Entry | ALB (Request Tracing) | Adds X-Amzn-Trace-Id header to all requests |
  | Instrumentation | OTel SDK / ADOT auto-instrumentation | Application-level trace generation |
  | Collection | CloudWatch Agent (sidecar container) | Receives OTLP traces on 4317/4318, X-Ray sampling proxy on 2000 |
  | Backend | AWS X-Ray | Trace storage, indexing, service graph generation |
  | Visualization | CloudWatch Trace Map + Application Signals | Service health, SLI/SLO dashboards |
  | Alerting | X-Ray Groups + CloudWatch Alarms | Per-service and per-path error/latency alarms |

- Key Decisions: (1) CloudWatch Agent as sidecar (one per task/pod) vs DaemonSet (one per node) — sidecar provides isolation but higher resource overhead; DaemonSet is more efficient for dense workloads. (2) Configure OTEL_EXPORTER_OTLP_TRACES_ENDPOINT environment variable pointing to the CloudWatch Agent (e.g., `http://localhost:4318/v1/traces` for sidecar, `http://cwagent-service:4318/v1/traces` for DaemonSet). (3) EKS: Use ADOT Collector as DaemonSet with X-Ray exporter for Kubernetes-native deployment.
- Scaling Path: At scale, DaemonSet pattern reduces sidecar overhead. Consider tail sampling in OTel Collector to reduce trace volume while keeping error/slow traces. Add CloudWatch Application Signals for automatic SLI generation.
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-services-ec2.html

## Provider Differentiators

**CloudWatch Unified Observability (Metrics + Logs + Traces in One Console)**
- Category: Observability
- Unique Value: AWS uniquely integrates distributed tracing (X-Ray), metrics (CloudWatch Metrics), logs (CloudWatch Logs), and application monitoring (Application Signals) in a single console with automatic correlation. Click a trace segment to see its correlated logs; click a metric anomaly to see the traces that generated it. No third-party tool provides this level of native AWS service integration.
- Architecture Impact: Eliminates the need for separate tracing, metrics, and logging tools when operating purely on AWS. Reduces context-switching during incident response. Enables alarm → trace → log workflows without leaving CloudWatch.
- When to Leverage: AWS-only architectures where operational simplicity and native integration outweigh multi-cloud portability concerns.
- Caveat: Tightly coupled to AWS ecosystem. If you need to send traces to non-AWS backends (Datadog, Grafana Tempo, Jaeger), you need the OTel Collector with multiple exporters.
- Source: https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-Application-Monitoring-Sections.html

---

**X-Ray Adaptive Sampling (Anomaly-Driven Trace Capture)**
- Category: Observability | Cost
- Unique Value: X-Ray's adaptive sampling automatically increases trace capture rate during detected anomalies, then reduces back to baseline after a cooldown period. This eliminates the operational pattern of manually increasing sampling during incidents (and forgetting to reduce it). Other providers require manual sampling adjustments or third-party tail sampling configurations.
- Architecture Impact: Enables cost-efficient baseline sampling (5%) with automatic high-resolution capture during incidents (up to 50-100%). Reduces the trade-off between observability cost and incident debuggability.
- When to Leverage: Production services with variable error rates where cost-efficient monitoring during normal operation must coexist with high-fidelity debugging during incidents.
- Caveat: Boost activation has a detection delay (anomaly must be identified before boost activates). CooldownWindowMinutes prevents continuous boosting but may miss back-to-back anomalies within the cooldown period. Only available with centralized sampling rules (not local JSON).
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-adaptive-sampling.html

---

**Parent-Based Centralized Sampling with Managed Reservoir**
- Category: Cost | Observability
- Unique Value: X-Ray's sampling model makes the decision ONCE at the root service and propagates it downstream, preventing sampling multiplication across microservices. The centralized reservoir is shared across all instances of a service (X-Ray manages per-instance quota distribution), preventing per-instance reservoir accumulation that plagues local sampling configurations.
- Architecture Impact: In a 50-service microservices architecture, sampling cost is controlled by a single set of rules at the entry point — not by 50 independent sampling decisions that compound. Reservoir sharing ensures the intended trace volume regardless of fleet size (auto-scaling).
- When to Leverage: Any distributed system with more than 3 services where consistent, predictable trace volume is required across auto-scaling fleet sizes.
- Caveat: Parent-based sampling means downstream services cannot independently increase their own sampling. If a downstream service has a bug only triggered by 1% of requests, and the upstream samples at 5%, you might capture it. But if you need guaranteed capture of specific downstream conditions, you need the downstream to start new traces (breaking the parent chain) or use tail sampling in the collector.
- Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-console-sampling.html

## Scenario Coverage

**Standard Case**: Microservices API with 5-10 services, moderate traffic (1K-10K RPS)
- Approach: ADOT auto-instrumentation on each service, CloudWatch Agent as sidecar/DaemonSet, API Gateway active tracing as root, centralized sampling at 1 req/sec + 5% rate, annotations for customer_id and deployment_version, X-Ray Group for error monitoring with CloudWatch Alarm.
- Key Decisions: Choose between CloudWatch Agent (simpler) vs OTel Collector (more flexible). Define annotation schema. Set sampling budget based on acceptable monthly X-Ray cost.

**Edge Case**: High-throughput event-driven system (100K+ events/sec via SQS/SNS) where trace context must span async boundaries
- Approach: Low sampling rate (0.1-1%) at the producer with adaptive boost. Ensure AWSTraceHeader system attribute propagation through SQS/SNS. For batch consumers (SQS batch of 10 messages), create a new trace per batch with link to parent traces via annotations. Accept that not all messages will be individually traced — use sampling statistics to extrapolate. For critical paths requiring 100% tracing, use dedicated high-priority sampling rules with targeted filter on message attributes.

**Anti-Pattern Case**: Team requests "100% tracing on all services in production" to "never miss an error"
- Clarification: Ask: "What is the monthly budget for tracing? At 100% sampling with 10K RPS across 10 services, you'll generate ~26 billion traces/month. At $5/million traces scanned, that's $130K/month in X-Ray costs alone. Can we instead use adaptive sampling (5% base + 50% boost during anomalies) combined with 100% sampling only on critical payment/authentication paths? This achieves near-complete error visibility at 1/10th the cost." Also verify: Do they actually need 100% tracing or do they need 100% ERROR capture? If the latter, tail sampling in the OTel Collector (keep all error traces, sample successful ones) achieves this at dramatically lower cost.

## OpenTelemetry Migration Reference

### Concept Mapping: X-Ray SDK → OpenTelemetry

| X-Ray SDK Concept | OpenTelemetry Equivalent | Notes |
|-------------------|-------------------------|-------|
| X-Ray Recorder | Tracer Provider + Tracers | OTel offers more configuration options |
| Service Plugins | Resource Detectors | Auto-detect EC2, ECS, EKS, Beanstalk metadata |
| Segment | Server Span | Automatic mapping by X-Ray exporter |
| Subsegment | Client/Internal/Producer/Consumer Span | Non-server spans become subsegments |
| Annotations | Attributes (added to `aws.xray.annotations` list) | Must explicitly mark as annotation |
| Metadata | Attributes (default) | All attributes become metadata unless in annotations list |
| X-Ray Emitter (UDP) | Span Exporter (OTLP HTTP/gRPC) | Export to CloudWatch Agent or OTel Collector |
| X-Ray Daemon | CloudWatch Agent / OTel Collector | Daemon is deprecated (maintenance mode) |
| Local sampling JSON | X-Ray Remote Sampler | Centralized rules from console |
| X-Ray Trace Header | X-Ray Propagator + W3C Propagator | Configure both for full compatibility |
| N/A | Span Processors | New capability: modify spans at creation/completion |
| N/A | Baggage | New capability: propagate key-value data across services |

### Migration Priority

1. **New applications**: Use OTel from day one — no X-Ray SDK dependency
2. **Critical production services**: Migrate instrumentation to OTel SDK, replace Daemon with CloudWatch Agent
3. **Stable low-change services**: Remain on X-Ray SDK (maintenance mode is safe for security patches), plan migration during next major refactor
4. **Lambda functions**: Use AWS Lambda Layer for OpenTelemetry (or ADOT Lambda Layer) — minimal code changes required
